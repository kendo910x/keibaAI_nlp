## 馬別の閲覧

- ホームの馬名検索と共通ナビゲーションに「馬別の解釈」を追加。記事検索にも、同じ語で馬別一覧へ進むリンクを追加した。
- `/horses?q=カランダガン` のように馬名の一部で探せる。候補やカードの馬名を選ぶと、その馬の完全一致へ絞る。全半角と空白の差は吸収する。外部馬IDの確定を前提にしない。
- **1記事の本文版・1頭につき1カード**。対象馬の解釈文、掲載元、掲載・更新表示、取得日時、解釈保存日時を表示し、保存原文との比較と掲載元記事へ進める。
- 試行計画・掲載元・掲載期間で絞り、20カードずつページ送りする。原文を開いて戻る際も馬名・絞込み・ページを保つ。
- 各URLの最新の取得が指す本文版、その版の最新の成功解釈を選んでから馬名を検索する。試行を指定した場合はその試行内の取得が対象。古い成功解釈だけが馬名に一致する場合に、それを新しい結果の代わりに表示しない。
- 旧Skillが同じ馬を複数itemへ分けた記録は、一つのカード内に全文章を保存時のまま表示する。「既存の分割解釈」と明示し、新しい要約が生成済みとは表示しない。
- 未解釈の記事は馬別の解釈件数へ含めず、元記事の検索と未解釈一覧への入口を残した。解釈0件を原資料の不存在とは表示しない。

表示時のモデル呼出し、DBへの書込み、管理操作の画面は追加していない。新モジュール `horse_view.py` は既存の `install-files.sh` の `runtime/*.py` に含まれる。DBスキーマの変更は不要。

## 解釈の単位と処理時間

### 分割が生じた指示を修正

変更前のSkillには、馬と競走、過去走と今回、事前と事後などを区別する指示があり、一方で「同じ記事の同じ馬は一つにまとめる」という単位が明記されていなかった。新Skillはその単位を先頭に置き、次のように整理した。

1. 記事内の離れた言及も、同じ馬なら一つの `text` にまとめる。必要なら同じtext内で段落を分ける。
2. 過去走・今回の調教・次走への希望、話者の違い、評価の理由、条件や留保は文章の中に残す。これらを別itemにする理由にはしない。
3. `race` と `phase` は主な競走の補助情報として維持する。主な競走を一つに定めにくいときはnullやmixedでよく、分割や外部照合で解決する必要はない。
4. 名前の羅列から所見を作らず、馬に属さない自然言語情報は必要に応じてhorse=nullで残す。全件の意味検証や厳密な正解率の条件は追加しない。

既存JSON形式との互換性を保った。重複馬の出力を理由に追加のモデル呼出しを繰り返す処理や、分割後に別LLMで統合する工程は作っていない。

### 17項目は17回の推論ではない

`poc/search_research/research.py` の `interpret()` は、保存した記事本文と掲載表示・取得観測日時を一つの入力としてモデルへ一度送る。返ったJSONの `items` を保存する構成で、itemごとにモデルを呼ぶループはない。デイリー記事の17項目という件数は、この出力の細分化に関する問題である。

細かい分割は回答量や分類・整理の負担を増やす可能性がある。ただし、新Skillで何秒短縮するか、遅さのどの程度が分割に由来するかは未測定。現行コードの `halogen-qwen3.8-flash-next`、Thinking有効、`reasoning_effort=xhigh`、最大65,536トークン等は今回変更していない。最大値が各記事の実際の使用量を意味するわけではない。

### 自動で全件をやり直さない

変更前の `pending_captures()` は、成功結果に現在のSkillハッシュ・モデル設定との一致を求めたため、Skillを変えただけで成功済みの記事も待機対象に戻り得た。現在は、同じ取得について日時付き入力形式で成功した結果があれば、自動の対象選択から外す。掲載表示の訂正で新しい入力を選ぶ動作と、明示した取得IDの有限再解釈は保つ。失敗入力の1日間の待ち時間は現在のSkill・設定に対して扱う。

これは自動対象選択の変更であり、稼働中の有限計画や成功記録を消去する処理ではない。

## 検証

ローカルの隔離環境で、表示と検索の回帰確認を実施した。実記事本文やVM15のデータはテストへ取り込んでいない。

- 同じ馬の7分割・複数競走・pre/postを一つの表示にまとめ、保存された文章と文脈を保持すること。
- 馬名の正規化と完全一致、他馬の文章の除外、HTMLのエスケープ、出典・日付・戻り先の保持。
- 空結果から元記事・未解釈記事へ進めること、ページ送り・絞込みの保持。
- Python構文、Skillの形式、差分の空白チェック。

**最終実行は31テストすべて成功。** 内訳は既存5件、馬別表示16件、実SQL10件。SQLは一時ディレクトリにリポジトリのマイグレーションからスキーマを作り、PostgreSQL 16.2のsingle-userモードで実行した。最新本文版・最新成功解釈を選ぶ順序、試行の範囲、7項目から1カードへの集約、21カードの20件＋1件のページ送り、Skill変更時の完了状態、日付訂正時の再対象化、失敗時の待ち時間を確認した。

```bash
KEIBA_SQL_SINGLE_USER=1 python -B -m unittest discover \
  -s infra/nlp-vm/runtime/tests -p 'test_*.py' -v
```

SQL検証用の `pgserver==0.1.4` とpsycopgはローカルの隔離環境にだけ導入し、本番依存には追加していない。通常のローカルDB起動はソケット作成を実行環境に拒否され、権限変更も自動拒否されたため、ソケットを開かない上記の方法で同じSQLを確認した。DB接続・psycopgの通信経路やVM15の実データでの動作まで検証したという意味ではない。SQLテストは `KEIBA_SQL_TEST=1` または `KEIBA_SQL_SINGLE_USER=1` による明示実行に限定し、指定がなければskipする。

新Skillと架空の短い記事を、別セッションのエージェントにも渡して指示の伝わり方を確認した。複数競走・話者を含む馬ともう1頭が、それぞれ一つのitemにまとまった。これは指示の簡単な確認であり、VM15のLocal LLMによる出力品質や速度の検証ではない。

## 実機で残る作業

1. 新コード・Skill・共通規約をVM15へ配備する。進行中の有限解釈の進捗を保ち、必要な再起動は記事単位の区切りで行う。既存配備スクリプトが現地Skill修正を保護した場合は内容を照合し、今回の方針が実際のSkillに含まれることを確認する。
2. 検証Dashboardの馬別一覧で、カランダガンなどの既存解釈、原文への遷移、検索条件を確認する。既存の分割解釈が表示上まとまることと、新Skillによる新たな要約を区別する。
3. 保存済みのデイリー記事など少数を明示し、検証領域で新Skillによる有限再解釈を行う。同じ本文・掲載表示・取得日時・モデル設定で、保存済みの旧結果と所要秒、思考・回答トークン、同一馬の件数、要約の読みやすさを比べる。通常会話に近い短い馬別要約依頼も比較するなら、同じLocal LLMへ同じ本文を渡す。

実機確認のために再収集する必要はない。本番へのデータ移行、全名簿、毎朝Cron、常駐解釈の開始は今回の作業に追加しない。保存済みの全記事を新Skillでやり直す処理も自動では起動しない。
