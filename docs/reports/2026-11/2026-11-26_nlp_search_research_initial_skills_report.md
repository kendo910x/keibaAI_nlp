## 初期Skillと研究用の保存方法

3役の初版は `2063f2a56ecd4b74c4d7c7d4ba4c148fe75f135d` に保存した。検索Skillには上の実例と切り替え方、分類Skillには既存の固定Bを基にした馬・レース・前後・自然文、統括Skillには次の子へ渡す対象・既知版・残件を書いた。[検索](../../../skills/keiba-search/SKILL.md)・[記事解釈](../../../skills/keiba-interpret/SKILL.md)・[親の統括](../../../skills/keiba-coordinate/SKILL.md)・[比較元の固定B](2026-11-25_nlp_stage3c_semantic_reconstruction_poc_report.md)

通常DBへの接続を持たない研究専用のstdio MCPを、VM15の既設Hermesコンテナ内で起動した。PCからも同じ補助コードを単発実行できる。共用サービスのYahoo検索とfetchが実通信を担当し、検索ID・順位から候補を選ぶ。記事本文が受領できたら、モデルを経由せず、ヘッダーとSTATUSの間の文字列を取得時刻・要求URL・最終URL・打切り表示と一緒に保存する。成功・拒否ともに観測IDが付き、最終URLと受領本文が同一なら版IDが一致する。[補助コード](../../../poc/search_research/research.py)・[CLIと研究用MCP](../../../poc/search_research/run.py)

補助コードと、子が規約を読む方法を追加した統括Skillは `4178956a2a65e7dfa0c7f372f57645dcb0fda491`。Pythonの構文とSkillの形式を検査した。機械処理の短い試験では、本文内の区切りと末尾空白を保持した。本文変更で版IDが変わり、出力打切り後にも原文から再試行できた。拒否応答に本文を作らず、キャンセル時も中断として記録できた。

独立推論には分類Skillをsystem、保存した一記事の本文をuserとして送る。親子の履歴・検索語・他記事の結果は入力に含めない。最終content、終了理由、使用トークン数、SkillのSHA、取得IDと版IDを別ファイルに残す。失敗後は取得済み本文から再開できる。同一版・同一Skill・同一設定の成功結果は再利用でき、明示的な再試行は別の推論IDになる。場面と既知の `domain_id=jra`・`race_key` はGit外の `subjects.json` で対応させ、記事が語る他の競走に探索対象のキーを配らない。馬名の機械的な検索にはNFKCと空白除去を使う。

Codex分で本文を持つ19観測は、保存した共用応答から取り直した文字列と全て一致した。うち6観測は8,000字のpartial。キャピタルSの展開説明は文の途中で切れ、古い調教記事の一つは月別アーカイブの途中で切れていた。同じpartialでも欠ける内容は異なる。Cookieやログインによる再取得はしていない。全件についてページ全体を取得したとの扱いはできない。

Hermes分を含む最終39観測は `ok` 21、`partial` 7、robotsで取得を見送ったもの10、共用fetchの `blocked` 1。本文のある28観測すべてで受領文字列と版IDを照合し、検索→取得→解釈の参照先を確認した。談話のまとめを約1時間後に再訪した例では4,803字から4,815字に変わったが、差分は「関連記事」の6件の見出しと紹介文に限られた。同一URLの版IDの変化だけでは主記事の加筆を示せない。[再訪したマイルCSのまとめ](https://keiba-iroha.com/mile-cs-2026-race-comments/)

## 継続収集に必要な差分

- **取得と版の照合。** 現行の通常DBではモデルが渡した文字列を保存する。研究では共用fetchの返却をコードが先に保存し、同一URLの再訪と本文の変化を識別できた。通常経路に移す際は、受領本文・版ID・取得時刻・打切りを返し、生成文を独立した成果として参照できるようにする。モデルによる本文転記を挟む必要はない。
- **記事の再処理と引き渡し。** 取得IDから一記事だけを分類できるようにし、入力版・Skill版・成功・失敗・中断を持つ。今回の親子では一記事の読解待ちで次の検索が数分以上止まった。深掘りが必要な版だけその場で読み、ほかは取得済み・未解釈のIDとして渡せれば収集を続けられる。研究MCPが子に返したのは項目数、馬名一覧、先頭3項目とID。20項目ある談話集で末尾の敗戦馬を深掘りするには、保存した解釈から馬名を指定して該当項目だけ読めるとよい。探索対象のレースと、文中の過去走・比較相手の意味を分け、日付や番号の不足で保存を止めない。
- **共用fetchの返却範囲。** 平文化された記事では見出しが残ってもリンク先がないことがある。今回は見出しを再検索して日別記事に着いた。8,000字で本文途中が落ちた例もあり、次工程では許容範囲の本文を先に保存し、LLM向けには小さく返す方法、必要時に主記事内のリンクを返す方法を検討したい。共用サービス自体の変更は別工程とする。

次の1開催は、注目重賞1競走と情報量の異なる特別1競走を組み合わせる案がある。事前は週初めの登録・展望と木金の調教・枠順で再訪の狙いを変える。事後は当日夕方に談話、週半ばに敗戦馬や次走を一頭ずつ調べる。過去資料は日常収集と別の枠で、開催年・出走予定馬を起点に1競走ずつ事前・事後を対にする。これらの間隔は今回の掲載日や検索の偏りからの提案で、定期実行は開始していない。

## 再開方法

開発PCのGit外の保存先は `%LOCALAPPDATA%\keiba-nlp-review\search-skills-20261126`。このディレクトリのACLは実行ユーザーとSYSTEM。VM15では既設 `nlp-hermes` コンテナ内の `/var/tmp/keiba-search-20261126` を使う。親ディレクトリはHermes所有の0700。日付・場面・既知のレースキーは `subjects.json`、検索・候補順位は `searches/`、受領本文・拒否は `captures/`、生成文・モデル・設定は `interpretations/` のIDから引ける。VM側のこれらのファイルは研究ディレクトリの `data/` 配下にある。

次の担当者・子への方針は「競馬の自然言語を広く大量に蓄積する。9割がた役立てば十分で、曖昧さ・少数の誤りを許容する。日時やIDの完全な証明を求めず、取得本文を残す。次週末の事前・前週末の事後・数年前の発掘を分け、検索、読解、Skill改善の判断は担当に任せる」。新しい親には対象、既知の取得ID、残った問いを添える。

今回の4競走の取得ID・既知の版・残った問いは、PCの保存先の `handoff.md` と、VMの研究ディレクトリの `work/handoff.md` にある。再開時は対象日と深掘りしたい問いをこの短い引き継ぎに書き、VMの通常の管理経路から新しい親を起動する。下記は今回と同じ設定で引き継ぎを渡す例である。

```sh
trial=/var/tmp/keiba-search-20261126
sudo podman exec --user 10000:10000 --workdir "$trial/work" \
  --env HERMES_HOME="$trial/profile" --env HOME="$trial/os-home" \
  --env XDG_CACHE_HOME="$trial/os-home/.cache" --env HERMES_INFERENCE_TIMEOUT=1800 \
  nlp-hermes sh -c 'exec hermes chat -Q --max-turns 14 -q "$(cat handoff.md)"'
```

一記事だけ扱うときはリポジトリの `poc/search_research/` で `python run.py interpret <取得ID>`、検索は `python run.py search <場面・対象> "<検索語>"`、取得は `python run.py capture <検索ID> <順位>` とする。PCではPython 3.14と[依存ライブラリ](../../../poc/search_research/requirements.txt)を使い、`KEIBA_RESEARCH_DIR` を上記のGit外保存先、`KEIBA_INTERPRET_SKILL` を分類Skillの絶対パスに向ける。強制再推論する場合だけ `interpret` に `--fresh` を付ける。

PCの同じ研究領域にある `resume-bundle.tar.gz` は、観測データ、3つのSkill、研究設定、補助コード、作業規約、引き継ぎをまとめたもの。研究用設定はコンテナ内の上記の絶対パスを参照する。コンテナ入替時には同じパスをUID 10000が使えるようにし、`os-home/` を用意してこの一式を戻す。今回確認したのは既設コンテナでの新しい親の起動とファイルの引き渡しまで。通常DBの移行、旧56版の再処理、v3変更、通常プロファイルへの配備は実施していない。

終了時には研究用のHermesとMCPの残存プロセスが0件だった。通常プロファイルの設定と旧収集SkillのSHA-256は開始時と一致した。再開用の一式は88ファイルで、収録した観測データとPC上のファイル、研究プロファイルの3つのSkillとリポジトリの正本が一致することを確認した。通常DBの行数比較や、運用規模での収集速度の測定は行っていない。
