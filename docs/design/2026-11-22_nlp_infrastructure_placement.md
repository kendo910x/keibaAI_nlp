## 2. 確定した方針（2026-11-22 ユーザー合意）

1. **配置**: ESXi `192.168.0.5` に **NLP専用VMを新設**し、専用DB・研究エージェント・後日のEmbeddingワーカーをそこへ置く。EVO-X2・mini-v3への新規タスク配置は行わない。Talos k8sの既存VMへの同居（RAMリサイズ等）も取らない。
2. **薄目のコンテナ化**: NLP VM内は **podman + quadlet（systemd unit）のみ**。k8s・Compose等のオーケストレーションは入れない。コンテナは消せる前提とし、データはホスト側ディレクトリ（例 `/srv/nlp/`）に置き、バックアップ・復元対象はホストのデータとダンプに限定する。
3. **共用検索**: 既存のgoogle-search-mcp（mcpo・ClusterIP）はk8sの現位置に維持し、段階1でNLP VMからも呼べるよう公開経路（NodePort等）と429・共有クールダウン・本文取得状態の改善を行う。Open WebUIからの既存参照経路は変更しない。
4. **LLM推論**: NLP VM上のエージェントは EVO-X2 のFlash-Next API（`192.168.0.13:8731`）をLAN経由で利用する。EVO-X2側に常駐物を追加しない。
5. **CPUシェア**: ESXiホストは4スレッドへの過剰割当となるが、収集が夜間バッチ主体で常時稼働率が低いため許容とする（ユーザー判断）。

## 5-1. 方針更新: 初期はv3連携を行わない（2026-11-22 ユーザー合意）

v3参照データの取込（引き継ぎ書 第7章・完了条件「v3参照によるレース・馬の照合」）は**初期段階では実施しない**に変更する。識別子はNLP側で自己完結させる。

- **レース**: `race_key = YYYYMMDD/JJ/RR` は記事本文から読める日付・競馬場・レース番号から構成でき、単独で一意。v3のレースマスタを要しない。v3と同一の書式を維持し、将来の結合に備える。
- **馬**: 正規化した馬名を `horse_key` の基礎とする。JRAは登録馬間の同名を禁止しており、当面の収集対象（近年のJRA）では馬名は実質一意とみなせる。
- **前提と緩和策**: 馬名一意の仮定には限界がある（登録抹消後の名前再利用、JRAとNARの別登録による跨ぎ重複、全角半角・長音・「号」等の表記ゆれ）。正規化規則を段階2で定義し、記事から取れる生表記・ namespace（jra/nar）・生年月日や年齢（取れた場合）・同定根拠を併記する。複数候補・保留を許容し、断定しない（引き継ぎ書 第6.2節の方針と整合）。
- **将来の再結合**: 予測研究段階で競走結果・オッズと結合する必要が出た時点で、`blood_reg_no` 等との対応表（マッピングテーブル）を追加する。v3側のDuckDB→汎用DBの日次同期（v3は追記主体なので増分同期が成立）はv3プロジェクト側の個別検討事項であり、NLPのクリティカルパスには置かない。実施される場合はv3側の承認済みタスクとして扱う。
