**次の作業は、既存の識別ルールを維持しながら、新しい記事処理方式に必要なDB・MCP・初期Skill・進捗管理を設計すること。**

- 従来の長時間収集・文字範囲登録は段階3C-2sの受入条件を満たしておらず、**不合格のまま**。長時間の継続収集3C-3には進んでいない。
- その後、「取得原文を通常コードで直接保存し、記事単位の独立推論で馬別の文章を再構成する」方式を検証した。長文1例では出力枠を広げて完結し、Hermes標準の子エージェントによるDB・Skillの引き渡しも合成課題で確認した。
- これらは個別の成立確認であり、**新方式の恒久DB/MCPや収集パイプラインは未実装**。
- 直前のチャットで示した**9テーブル・7ツール案は撤回済み**。承認済み仕様として実装しない。現行8テーブルをそのまま恒久仕様に固定するとの合意も、新しい表数・ツール数の合意もない。
- 通常の馬識別は馬名、レース識別は開催年月日・競馬場・レース番号という既存合意を維持する。v3マスタ取込を初期収集の前提に追加しない。

## 1. 維持する目的と合意

### 1.1 研究の目的と想定する使い方

NLPは、既存の `keibaAI_v3` から独立した研究プロジェクトである。目的は、自然言語情報を広く蓄積し、人間向けの整理・要約と、別の統計・機械学習モデルによる追加予測力の検証に使うこと。LLM自身に勝ち馬を予想させることは必須ではない。[共通規約][agents]

| 想定用途 | 保存・抽出で必要になること |
|---|---|
| あるレースの下馬評・回顧を要約する | 対象レースに関する各馬の見解とレース全体の文脈を、事前・事後を区別して取得できる |
| ある馬の履歴と次回走について要約する | 馬を軸に過去走・今回の見解をたどれる。過去走が今回の評価の根拠になっている関係を落とさない |
| レース単位・馬単位でv3のデータと結合する | NLP側の識別を維持し、必要になった段階でv3のキーへ対応付けられる |
| 事前記事に追加予測力があるか検証する | 対象レースのpre資料を抽出し、結果・既存予測・市場情報等と別工程で評価できる |

**データ蓄積後に最初に試したい研究シナリオは、レース前の記事による追加予測力の検証。** レース後の記事を同じレースの事前入力へ混ぜない。

中核は「文章・対象馬・対象レース・前後区分」。新方式では文章を取得原文とLLMによる再構成文に分ける。話者・調教師・騎手・時計・好不調・期待度などを大量の固定列やスコアに展開する方針は採らず、必要な意味は文章内に保持する。[DB仕様 §1.1][db-instruction]、[再構成PoC指示][semantic-instruction]

### 1.2 馬・レースの識別 — ここを再び前提から変えない

ユーザーの最新の訂正は、既存合意を確認せず識別方式を再設計したことへの指摘である。次の担当者は以下を前提にする。

| 対象 | 維持する論理的な識別方針 | 現行DBの物理実装 |
|---|---|---|
| 馬 | 想定する近年JRAの通常ケースでは、正規化した馬名で同じ馬を識別する | `horse_id`はUUID主キー。`normalized_name`は非一意索引 |
| レース | **開催日（年を含む）・競馬場・レース番号**で識別する。表現は`YYYYMMDD/JJ/RR` | `race_id`はUUID主キー。`domain_id`と`race_key`がともに判明した場合に部分一意 |
| v3との関係 | 初期はNLP側で自己完結。v3マスタの取込を要求しない | 将来、必要時に`blood_reg_no`等との対応を追加する余地がある |

11月22日の[配置設計 §5-1][placement]に、初期v3連携なし、馬名を識別の基礎にすること、レースキーをNLP側で構成することが明記されている。11月24日の[DB仕様 §4.3〜4.4][db-instruction]と[実DDL][ddl]では物理主キーがUUIDになっている。**内部の参照IDと、同じ馬・レースをどう認識するかは別の問題であり、UUIDがあることを理由に通常の馬名識別を取り消さない。**

馬名の正規化は現行仕様ではNFKC＋Unicode空白除去。長音・記号・「号」などを勝手に削除しない。同名再利用や対象範囲をまたぐ曖昧さは既知の例外であり、情報不足の際は候補・保留を許容する。例外を理由に、通常の収集すべてへ外部ID照合や追加確認を義務付けない。

一方、今回の訂正を「ただちに馬名へ物理UNIQUE制約を追加する指示」とも解釈しない。物理DDLや同定APIの変更が必要なら、現行実装との差分として次の設計で示す。

実装上の残件として、DB仕様例の`jra / nar_thoroughbred`とMCP・保存済みデータの`JRA / NAR`に表記差がある。競馬場コードとdomainの表現を整理する必要はあるが、これは識別ルールを捨てる理由にも、v3全体の取込を必須にする理由にもならない。[DB仕様][db-instruction]、[現行MCP][server]、[品質調査 Q1][quality]

### 1.3 レース前・後の扱い

`pre / post / mixed / unknown`は、**対象レースとの関係**を文脈から判断した値として扱う。記事全体へ単一のフラグを付ければ済むとは限らず、一つの記事に今回の展望と過去走の回顧が共存する。

- 当該レース後の記事が発走前の心境を引用していても、その回想を当該レースの事前資料に変えない。
- 過去走の結果や談話が、次走を考える資料になることはある。
- 公開日時が不明でも収集・分類を進められる。日時の追加調査や公開時刻との機械比較を主判定にしない。
- `pre`という分類だけで、実際にその時点で公開・取得できたことを証明したとはみなさない。分類ベースの歴史資料研究と、厳密なas-of検証を区別する。
- 馬の集合とレースの集合を直積して関連付けない。各文章が実際に何について述べているかを保持する。

初期収集へ大規模な時点証明・証拠管理基盤を戻す合意はない。研究時の明らかな事後混入や、同一発言の転載・同一URL別版の重複には注意する。[DB仕様 §4.6][db-instruction]、[長文再検証][budget]

### 1.4 LLM・通常コード・Skill・Embeddingの役割

| 担当 | 役割・方針 |
|---|---|
| Hermes＋Local LLM | 探索、追加検索の判断、文章の意味理解、馬・レース・前後の判断、経験をSkillへ反映する活動 |
| 記事単位の独立推論 | 取得原文と分類指示を読み、意味を保った馬別・レース別の文章を生成する方向。長い生成履歴を探索セッションへ戻さない |
| 通常コード | 取得内容の直接保存、ID・hash・重複・整合性、推論呼出し、出力検査、保存、処理済み判定・再開、SQL抽出 |
| Codex | 初期の検索Skill・分類Skillを調査・試行して作成し、実装と独立評価を行う |
| HermesのSkill更新 | 用意した初期Skillを実作業で使い、経験によって自発的に改善する |
| Embedding | 収集とは独立した後続工程。未生成でも蓄積・通常のSQL抽出を妨げない |

Codexが初期Skillを作り、Hermesが経験で改善する方針、および速度・トークン節約より情報保持・解釈品質を優先する方針は、このスレッドでのユーザー意向である。旧3B時点の「初期Skillを手書きしない」を、そのまま現在の制約にしない。

Thinkingの停止・低減や小さい出力枠を既定の解決策にしない。サーバー上限とcontextの範囲内で、完結に必要な生成枠を確保する。最新の試験値と、まだ通常運用へ配備していない設定は第5節で区別する。

記事解釈を独立した呼出しにすることは、探索と理解のフィードバックをなくすことではない。分類で分かった馬・過去走・不足情報を次の探索判断へ返せるようにする。Embeddingだけは別工程のままでよい。[再構成PoC指示][semantic-instruction]、[委譲検証指示][delegation-instruction]

### 3.2 現行8テーブル — 実装済みの構造

以下は次の設計案ではなく、基準版の実DDLを要約したものである。[現行DDL][ddl]

| テーブル | 主な内容 | 最終確認件数 |
|---|---|---:|
| `collection_runs` | run ID、task/progress JSON、status、開始・更新・終了日時、エラー | 3 |
| `articles` | 記事の取得内容1版。URL、任意の媒体・タイトル・公開表記、本文、本文種別、hash、取得時刻、run ID | 56 |
| `horses` | 内部UUID、馬名、正規化名、任意の生年 | 68 |
| `races` | 内部UUID、名称、開催日、domain、race_key | 16 |
| `text_units` | 記事版IDと原文内の開始・終了文字位置。独立した生成本文は持たない | 207 |
| `unit_targets` | unitに対する馬・レースの必要な組、未同定時のラベル、前後区分 | 750 |
| `embedding_configs` | モデル・revision・次元・前処理/分割設定・設定hash | 0 |
| `embeddings` | unit・設定・chunk、範囲、数値ベクトル、生成時刻 | 0 |

現在の重要な契約は以下のとおり。

- 同じURL・本文種別・本文hashは同一記事版として扱い、IDと初回記録時刻を再利用する。内容が変われば別版、別URLなら出典を保持するため別行とする。
- `body_kind`は`full / excerpt / snippet / none`。`none`以外には非空本文と対応hashが必要。
- 本文がある記事は全文unitを自動生成する。部分unitはUnicodeコードポイントの0起点・半開区間で原文を参照する。
- `unit_targets`は馬だけ・レースだけも許す。ただし馬とレースを同時に必要とする用途では、実際の関係が保存されている必要がある。
- `save_targets`には、逐語quoteが一意なら通常コードで位置を決める処理が既にある。文字位置計算をLLMへ任せる必要は本来なかった。
- 現行の`text_units`は原文範囲モデルなので、**LLMが再構成した独立の文章を保存する物理モデルは未実装**。生成文を`articles.body`へ上書きしたり、架空の原文オフセットで表現したりしない。
- Embeddingは未生成。モデル・設定ごとに区別する仕組みはあるが、新しい再構成文を入力にする場合の参照先・再生成契約はこれから整理する。

根拠: [DB仕様][db-instruction]、[DDL][ddl]、[引用位置解決][targets]。

56記事版は51 URLに由来し、5 URLに2版ずつある。`full`19版・`excerpt`37版。全文unit56、部分unit151。750関連行のphaseはpre448・post296・mixed6・unknown0。ただし、これらは現在の登録値であり、正しい原文保存・正しい意味分類を保証する数字ではない。[品質調査 Q1][quality]

## 4. 従来方式で何が起きたか

### 4.1 収集の進捗と停止

| 試行 | 新規版 | 累計 | 主な到達点・停止 |
|---|---:|---:|---|
| A | 10 | 10 | 2025年皐月賞で検索→取得→保存→関連付けが一巡。約10分で正常終了 |
| B | 10 | 20 | JRA/NARを探索。IDとラベル同時指定のエラー反復で約20.7分後に管理側停止。その後ID優先に修正 |
| B2 | 19 | 39 | 2026年1月JRA9競走の台帳を作成。約21.2分で圧縮失敗が続き終了 |
| B3 | 17 | 56 | 同じ9競走を継続。約30.7分後、入力263,064がcontext262,144を920超えてHTTP 400 |

品質調査で、B2の最後のエラーは主要求の`max_tokens=131072`がサーバー上限65,536を超えたこと、B3は入力context超過であることを区別した。両者とも確定した圧縮前後の削減量は得られず、B3の時間が長かったことだけで設定改善の効果量を主張できない。[品質調査 Q6][quality]

9競走のうち5版以上あったのは中山金杯・京都金杯の2競走。日経新春杯1版、他6競走0版だった。B3新着17版の馬別部分範囲は0/229組、全試行では110/487組。従来の受入条件を満たさず、3C-2sの判定は不合格である。[収集状況][collection]

「各競走5版」「馬別範囲90%」等は当該試験の受入条件であり、新方式の恒久的な収集件数ノルマとして転記しない。

### 4.2 保存済みデータの品質調査で分かったこと

**保存関数が受け取った文章は保存できていたが、受け取る前にLLMが原文を改変していた。**

全56版で`save_article`引数とDB本文・hashは一致した。一方、取得応答との全長一致または一つの連続部分としての一致は0/56。これには不要箇所の除去等も含まれ、全56版が意味的に誤っているという意味ではない。しかし実際に、オッズ表で14頭中13頭の枠番が変わり、14頭全ての複勝レンジ上限が欠落した例がある。[品質調査 Q2][quality]

ほかに次の問題があった。

- 750関連行のうち、馬だけ530行、レースだけ121行、両方99行。部分を持つ馬×記事110組でも、同じtarget行にレースが入るのは38組。馬とレースを同時指定すると、存在する情報が検索から落ちる。
- 一部で別レースの記述や関連記事案内が混入し、公開日時欄へ発走時刻が入る例もあった。`full`という保存種別だけで原文完全一致とは扱えない。
- S1〜S4の`save_slices`は23呼出中10呼出が拒否。拒否に含まれる71引用は、既存の引用検索で全て一意に位置を決められた。
- S4の約59〜60分・`get_article`94回は2記事と全体索引調査を含む。指定アギョウ記事の読み出しから保存までは10分03秒。「その1記事に60分」とは記載しない。
- 自動作成された収集Skillには、有用な探索経験とともに「全頭へ一括付与」「取得可能ドメインの固定」「旧ツール仕様」等の不適切・古い記載が残った。
- 検索候補を得た後に取得へ進めなかった競走、そもそも専用検索をしていない競走がある。「情報が存在しない」と「探索していない」を区別する必要がある。

当時の取得本文はHermesの`state.db`に残る。表示用run JSONLの5,003字制限や、`result`と`structuredContent.result`の二重表示を原文欠落・二つの別資料と誤認しない。[品質調査 Q2〜Q7][quality]

以上から、原文の転記と文字位置合わせを中心に改良するだけでは不十分と判断し、意味再構成のPoCへ進んだ。

## 5. その後の検証で確認できたこと

### 5.1 記事単位の意味再構成PoC

実記事9種＋架空1本に対して、最小指示AとCodexが改善した分類指示Bを比較した。Hermesを起動せず、既存Halogenへ記事ごとに新しいsystem＋userで直接推論。入力はDBの編集済み本文ではなく、当時の取得応答を機械的に復元したもの。[再構成PoC][semantic]

- 初回の形式適合はA8/10、B9/10。確認用6件は両方5/6。**これはJSON契約への適合数であり、意味品質の正解率ではない。**
- Bは11頭の事後談話を、正しい馬のpostとして保持した。
- 複数馬の比較、1ページに複数競走がある記述、否定・条件・時計、離れた補足の統合に成立例があった。
- 所見のないオッズ表ではBが`items=[]`を返した。数表だけから新しい論評を作る必要はない。
- 単位や節の時期の省略、レース全体の文脈が馬別検索から落ちる点、長文の出力打切りは残った。

初回20＋再試行4の計24要求、経過78分32秒。試験の`items[{horse,race,phase,text}]`は能力確認用の出力形式であり、永久的なID契約・DB構造・MCP仕様の承認ではない。分類指示Bの全文とhashはレポートにあり、初期分類Skillの出発点として使える。

### 5.2 出力枠65,536による長文1例の再検証

同じ京都金杯記事の取得範囲8,000字、同じ固定指示Bに対して、要求の`max_tokens`だけを変更した。[長文再検証][budget]

| 項目 | 前回 | 再検証 |
|---|---:|---:|
| 出力上限（thinking込み） | 32,768 | 65,536 |
| 実際の出力tokens | 32,768 | 48,571 |
| うちthinking | 27,878 | 43,098 |
| 回答tokens | 4,890 | 5,473 |
| 終了 | `length` | `stop` |
| 所要時間 | 416.0秒 | 587.3秒 |
| 未修正JSON | 不成立 | 成立、39項目 |
| 個別所見 | 18/23頭まで | 23/23頭 |
| 週前・最終の評点 | 全46中36 | 46/46 |

39項目は馬別pre23、レース全体pre10、過去走post6。thinking有効、配備既定xhighで完結し、この例では記事分割やthinking低減を必要としなかった。

評価したのは**取得時に8,000字で打ち切られた保存範囲**であり、元Webページ全体の完読ではない。必要な所見・展開・最終印の節は入っていた。出馬表にない5頭への所見も正しく残ったが、pre資料があることから出走確定を推定してはいけない。

残る設計上の要点は、現在のpreとその根拠である過去走post、レース全体の条件を一緒に取得できること。異なる節の評価差や時期も文章で分かるようにする。この1例を、さらに長い記事や全媒体での忠実性の保証へ広げない。

### 5.3 Hermes標準サブエージェントの実機検証

通常環境から隔離したプロファイルと一時試験DBで、短い合成課題を実行した。[委譲検証][delegation]

| 検証 | 確認できたこと | まだ確認していないこと |
|---|---|---|
| 親子分離 | 新しい子はsystem＋新しいuserで開始。親や前の子の中間履歴がそのまま流入しない | 実記事で長時間動かした場合の親context維持 |
| MCP継承 | 親19ツール、leaf子17ツール。同じ記事版をA・B・親・独立SQLで照合 | この実験でのYahoo実検索・外部記事取得 |
| Skill継承 | 子Aが作ったSkillを、新しい子Bが読んで適用できた | 自律的に改善する競馬Skillの品質 |
| 未完了後の継続 | 反復上限で未完了の子Cの後に、独立した子Dを起動できた | VM再起動・親消失・通信断・途中推論の自動復元 |
| 出力指定 | 親子の観測HTTP17要求で`max_tokens=-1`を送信し、HTTP200 | 各要求で実際に確保された最大枠の数値、長文分類の再現 |

**業務の完了判定に重要な観測:** 未完了の子Cにも`status=completed`が付いたが、`exit_reason=max_iterations`、`truncated=true`で、DBには最初のstepしか書かれていなかった。通常コードで終了理由・打切り・保存済み成果を照合して完了を判断する必要がある。

親に返るものは最終要約だけでなく、状態・終了理由・tokens・所要時間・tool trace・transcript参照も含む。親側の履歴増加がゼロになるわけではない。

試験は子を1件ずつ順次起動した。並列化は必須ではなく、今回も並列競合を検証していない。短い合成課題のthinking=mediumを、記事分類のxhighを下げる根拠にしない。`max_tokens=-1`は無限生成ではなく、サーバー上限と残context内の最大枠を求める指定。これらは**試験プロファイルの設定**で、通常構成へ配備済みではない。

試験DBは削除、HBAは復元、試験プロファイルは回収済み。通常DB・設定・Skill・Memory・既存資料は前後一致。3C-2sの不合格判定を変更する実験ではなかった。

## 6. 新方式の方向と、まだ決めていない設計

### 6.1 方向として維持すること

1. 許容される取得原文を通常コードが直接保存する。LLMに本文を書き写させない。取得が一部だけなら、その範囲と取得状態を保つ。
2. その原文を記事単位で独立した推論に渡し、馬・レース・前後ごとに意味を保った自然言語へ再構成する。
3. 再構成は情報を意図的に減らす要約ではない。引用、主語補完、比較の分解、離れた補足の統合、言い換えを必要に応じて使い、否定・条件・数値・単位・留保・帰属を保持する。
4. 再構成文はLLMの解釈結果として、元の取得版と結ぶ。原文や逐語引用として偽装しない。
5. 親Hermesが対象・進捗・追加探索を統括し、子を順次起動する構成を設計の基礎にできる。記事分類の大量の生成履歴を探索の会話へ持ち込まない。
6. DBとSkillをセッションから独立した引き渡し先にし、通常コードが処理済み・未処理・失敗を判断できるようにする。

これは[再構成実験の合意範囲][semantic-instruction]、[長文の実測][budget]、[委譲構想と実測][delegation-instruction]を踏まえた方向である。次の表の詳細仕様まで確定したものではない。

### 6.2 次に具体化する事項

| 設計論点 | 決める内容 | 維持する制約 |
|---|---|---|
| 取得と保存の境界 | fetch結果から直接保存する経路、保存可能範囲、打切り・失敗の扱い | 原文をLLMの出力から再作成しない |
| 再構成文の保存先 | 原文版とのFK、文章単位、馬・レース・phaseとの関係 | 現行原文範囲モデルへ無理に押し込まない |
| 馬・レースの解決 | 馬名照合、日付・競馬場・番号からのkey、未知情報の扱い、domain表記 | 第1.2節の既存合意を維持。v3マスタを前提にしない |
| まとめて取り出す範囲 | 今回pre、根拠の過去走、レース全体の条件、馬のみの情報の取得方法 | 馬×レースの直積や単純な全頭割当をしない |
| 処理の識別・再開 | 記事の入力版、使用した分類指示、処理段階、保存結果、完了の判定 | 巨大な証拠管理表群に戻さず、必要な再実行管理だけを持つ |
| 再処理・採用結果 | 同じ入力への再試行、Skill変更時の再解釈、現在採用する結果、失敗時の扱い | 原文を上書きせず、部分JSONの自動修復を成功としない |
| MCPの責務 | 取得・保存・分類呼出し・関連付け・進捗・検索結果の返却量 | 9テーブル・7ツール案の名称・個数から設計を始めない |
| 親子の実行契約 | 子の単位、親子の反復枠、総子数、順次実行、HTTP期限、出力枠、終了条件 | 合成試験の設定値をそのまま恒久値にしない |
| 初期Skill | 検索・分類・統括の契約と改善方法 | Codexの初期研究とHermesの経験更新を両立する |
| Embeddingの入力 | 原文／再構成文の参照、モデル版、長文分割、再生成 | 収集をEmbedding実行の成否に依存させない |
| 旧データとの関係 | 56版・旧索引の保全と、新方式で処理する範囲 | 全件移行を先に必須化しない。旧PoC24件は移行しない |

特に、PoCの馬・レースの自然言語文字列をそのまま永久の識別子とする案、全記事を固定長で分割する案、全頭へ同じ本文を割り当てる案は、採用済み仕様ではない。

## 7. 今後の作業計画

以下は再開時の順序である。**直近の成果物はレビュー可能な設計書と実装指示書**であり、本書だけで実機移行や長時間収集を開始しない。

### 7.1 合意・現行実装・新方式を一つの設計にする

まず第9節の資料を読み、用途から必要な保存・取得の契約を整理する。最低限、次を同じ設計書で示す。

- 何をどの表に保存し、原文と再構成文がどう結び付くか。主キー・外部キー・一意条件・更新可否。
- 馬名とレースキーが、同定・DB参照・将来のv3結合のそれぞれでどう使われるか。
- レース別・馬別・レース×馬別・pre抽出の具体例。過去走とレース全体の文脈を含めた取得例。
- LLMへ渡す入力、LLMが返すもの、通常コードが生成・検査・保存するもの。
- 中断後の再開と同一入力の再実行で、何を根拠に重複・完了・未完了を判断するか。
- 現行8テーブル・11ツールとの差分と、既存56版の保全方法。

表数を先に決めず、これらを説明できる最小の構成にする。既存の合意を変える必要があるなら、変更箇所・理由・影響を具体的に示す。採用していない代案を承認済み仕様として混ぜない。

### 7.2 初期Skillを具体化する

分類Skillは、再構成PoCの固定Bを出発点にする。残る課題は、過去走の根拠とのつながり、共通条件、節の時期・出所、意味のある単位・数値の保持。既知の成功例・失敗例を再利用し、一般的なLLM能力評価からやり直さない。

検索Skillは、これまでの検索語・到達先・未探索方向・ブロック例を踏まえてCodexが作る。特定媒体の固定リストに閉じず、取得できた情報が追加探索へつながるようにする。ユーザーの目的に無関係な一律件数や全頭網羅を強制しない。

統括の指示には、子へ渡す対象・既知情報・Skill名・処理範囲、返す短い成果と未完了、終了・再開の条件を含める。作成するSkillの管理・配備方法も実装指示にまとめる。

### 7.3 合意した差分を実装する

DB変更、MCP、直接分類呼出し、Skill、通常プロファイルを、採用した設計の範囲で実装する。現行データの削除や暗黙の上書きを前提にせず、変更前の状態と復帰手順を具体化する。既存の同定・保存・hash・抽出処理を使えるところでは再利用する。

この段階で、旧README・実行契約・DB説明と新方式の矛盾を解消する。今回の引き継ぎ書作成では既存DDL・設定を変更していない。

### 7.4 少数の実記事で、つながった経路を確認する

個別のモデル能力試験を繰り返すのではなく、未検証の統合部分を確認する。

| 確認点 | 必要な観測 |
|---|---|
| 原文保存 | fetchで受け取った保存対象とDB本文・hashが一致する |
| 記事分類 | 原文版が固定され、生成が正常完結し、再構成文として別保存される |
| 同定・関連 | 同じ馬名・同じレースkeyを再利用し、馬×レースの必要な組が取れる |
| 利用時の取得 | レース要約、馬履歴、pre抽出で根拠や共通条件を読み落とさない |
| 再実行 | 同じ成功処理を重複させず、失敗・打切りを完了にしない |
| 子の継続 | DB・Skill・短い引き渡しから次の子が続けられる |

既に品質を照合した入力と、少数の追加例を目的に応じて使う。件数・実行枠・終了条件は実装指示で具体化する。何時間も回すこと自体を成功条件にしない。

### 7.5 継続収集、Embedding、予測力研究へ進む

統合した小規模試験が成立したら、複数レースを順次扱う収集と、中断後の再開を確認する。以前の3C-2sと新方式の受入条件の対応を示し、新しい完了根拠を記録する。

その後、承認した対象・期間で蓄積を広げる。Embeddingは独立したバッチで生成し、レース前の記事による追加予測力を評価する。v3との対応はこの用途に必要な範囲で設計し、読み取り専用参照・exportを基本とする。v3本番DB・Hist/Live・購入設定・Autobet・Dashboardへ変更を混ぜない。

| 名前の例外がある＝v3マスタ必須 | 既存合意に反する。通常の名前・レースkey同定を維持する |

ESXiホストの約37時間23分の時計遅れは、段階2A時点で残った別件。VM15のchrony同期は確認済みだが、ホスト時計の是正完了は本書では確認していない。NLPの設計・収集作業へ無断で混ぜない。[VM復旧][vm-recovery]

当初の調査で別サービスのBasic認証情報付きURLがツール出力へ露出した件は、公開報告に実値を含めていない。資格情報の変更完了は未確認であり、必要なら独立して扱う。値を再掲しない。

バックアップ運用は初期PoC段階では延期した。その後の3B引き継ぎでは、段階4の本格蓄積に入る前にDB・HermesのSkill/Memory/Session等のバックアップを設計・整備し、復元を確認する計画となっている。保存先・頻度・保持期間は未決で、通常運用のバックアップ・復元確認が完了したとは扱わない。後続の運用設計で具体化する。[配置設計 §5][placement]、[3B引き継ぎ §8.2][handover-3b]
