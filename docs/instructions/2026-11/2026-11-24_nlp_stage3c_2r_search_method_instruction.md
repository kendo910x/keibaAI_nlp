設計出典: 段階3C-2レポート §6（観察入力の正本）、ユーザー決定 2026-11-24
前提: shared.3現行（JRA/NAR公式可読・回帰なし実測済み）。Bの残骸（articles 20・run B status=running）は保全したまま、新run_idで別ランとして実行する。

## 1. 目的とユーザー決定（2026-11-24）

Bは機械系（日程自力発見・race_key・Skill）は機能したが、**収集量・事前記事比率が実質未達**（3か月でB追加10件・post 78/105）。原因は (1) 台帳の自主縮小 (2) 検索語が事後偏り (3) 排他トラップによる律速。本ラン（B2）はこれを是正して**Bの合格ラインを満了する**ことが目的で、マラソンはB2合格後。

ユーザー決定:

1. **範囲は広くしない。2026年1月に実施されたJRA重賞（G1〜G4）を対象**。金杯がG4のためG4まで含める。台帳（1月にどの重賞が開催されたか）はJRA公式カレンダーから自力導出する（一覧は指示しない — 発見が課題の一部）
2. **検索の仕方の発見を課題に組み込む**。種明かし: 「『2026 金杯』検索では事後情報（結果・払戻）ばかりで研究価値が低い。『2026 金杯 追い切り』なら事前情報が出る」
3. **排他トラップの仕様変更を承認**: race_id/horse_idとlabelの両方指定時は**ID優先でlabelを黙って無視**（horse側も同様）。排他エラー経路を消す
4. **停止条件は正味進捗ベースへ再設計**: ガード停止回数ではなく「30分正味進捗なしで停止」
5. phase pre 60%以上を承認（救済: 特定レースで構造的に事前記事が存在しない場合は、その旨の証拠をレポートに残せば台帳分母から除外可）

## 2. 管理側変更（VM15）

### 2.1 targets.py: 排他仕様変更（ID優先）

`save_targets` の排他チェック（`Both {key} and {label} were given...` をraiseする箇所）を仕様変更:

- **idとlabelが両方指定されたら、label側をNoneにして進行**（raiseしない。idが正）。更新時（currentあり）も同様
- docstringに `When both an id and a label are given for one entity, the id wins and the label is ignored.` を追記
- 挙動不変点: label単独・id単独・どちらも無しは現状どおり。スキーマCHECKは変更しない（サーバー側で先に解決するため発火しない）

### 2.2 tests/contract.py

Bで追加した「両方指定→エラー」assertケースを**新仕様の挙動テストに置換**: race_id+race_label同時指定で**成功し、行のrace_labelがNULL・race_idが指定値**であることをassert。horse側も1ケース追加。実行できれば試験DB（keiba_nlp_stage2b_test）を3B手順で再作成して本体ごと実行。できない場合は実MCP呼出での代替実測をレポートに記録。

### 2.3 build・反映

B §2.3準拠（repo→`/srv/nlp/hermes-runtime/build/`→podman build→systemctl stop/start）。前後image ID記録。単発CLIで両方指定が成功に変化したことを実測確認。AGENTS.md・config.yaml・server.pyは不変。共用検索側は変更ゼロ。

## 3. ランB2の実行

**役割分担**: ランB2の実行者はVM15コンテナ内のHermesエージェント（nlp-hermes）であり、検索・取得・保存・Skill作成を含む研究タスクの判断と実行はすべてHermesの裁量である。コーディングエージェント（実施担当）の工作是起動・観察・実測・記録までであり、研究タスクを代行しない（検索結果を自分でsave_articleしない等）。

- 実行: B同経路（tmux→`podman exec --user 10000:10000 --workdir /opt/nlp-research nlp-hermes hermes chat -Q --format stream-json --max-turns 1200 --query-file /dev/stdin`。タスク文は`--query-file`でHermesへverbatim転送し、コーディングエージェントが解釈・補足しない）。外側 `timeout 19800`（300分+余裕）
- **停止操作の教訓（B §3）**: pkillパターンは実コマンドライン（`python -P -c "...main()) chat -Q..."`）に一致させる。停止確認はプロセス一覧＋ログサイズ不変の2点
- タスク文（この文面をそのままverbatim与える。これ以上の指示を足さない）:

> 研究タスク: 2026年1月に実施されたJRA重賞（G1・G2・G3・G4）に関連する競馬記事を集めてください。
> 最初のステップは検索方法の発見です。収集を始める前に、金杯を例に検索の仕方を試してください。「2026 金杯」と検索すると事後情報（結果・払戻）ばかりになります。事後記事は研究上あまり価値がありません。「2026 金杯 追い切り」などと検索すると事前情報が大量に出ます。追い切り・枠順・オッズ・予想・コース展望・厩舎訪問・登録馬などは一例です。いろいろな検索語を実験し、どんな検索語が事前記事を出し、どれが事後しか出さないかを切り分けてください。見つけた効果的な検索パターンは自分のスキルに記録してから、全レースの収集に進んでください。
> レース一覧はJRA公式サイト（ https://www.jra.go.jp/ ）を必ず参照して、2026年1月にどの重賞が実施されたかをご自身で確定してください。
> 記事集めはyahoo_searchで検索し、fetch_pageで本文を取得し、save_articleで原文を保存し、save_targetsで馬・レース・前後（phase）を索引付けしてください。1レースあたり10本以上、事前記事を優先して集めてください。
> 検索語・情報源・展開の方法はあなたの判断で自由に決めてください。予算: 経過300分まで。予算を使い切るか、新しいURLが出なくなったら終了してください。進捗と終了理由はsave_runに記録してください。

- 実行中の人間介入はしない
- 再実行増殖テスト: B同様1件

## 6. 停止条件（再設計）

- **正味進捗停止**: articles・unit_targetsのどちらにも30分新規行が無い場合のみ停止（`updated_at`/insert時刻で判定。ガード停止・リトライ失敗だけでは停止しない）
- 外側timeout 19800秒超過 → 進捗保全して報告
- 禁止行為の試行が観察された → 即時中断・保全・報告
- 連続429・ブロックが解消しない → 保全して停止（B同様）
