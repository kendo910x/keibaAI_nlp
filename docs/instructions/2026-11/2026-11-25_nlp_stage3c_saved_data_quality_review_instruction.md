## 4. 保存済み記事の実態（全56版を基本に調査）

### 4.1 全件概要

開始時のデータ集合を固定し、全記事版をCodex自身が本文と登録関係を読み、短い概要一覧を作る。レース台帳と収集記事の関係、A/B/B2/B3由来、同一URL別版、本文欠落等を区別する。B2/B3が同じrun_idであるため、ログの実save_article結果・collected_atと試行の開始終了時刻で分離し、判別不能は不明とする。時刻はJST/UTCの変換を確認する。

一覧の項目は article_id（識別可能な短縮可）、出典URL・媒体・タイトル（秘密/署名等のqueryは公開しない）、取得種別、文字数、実際の内容の短い要約、対象レース、馬の関連数（全文/部分を区別）、phaseの分布、取得本文の品質と利用上の気付き。既存本文の範囲外を推測しない。

集計:
- 記事版数・ユニークURL・媒体別、取得種別と文字数分布。全文/抜粋/snippet/noneの実態、同一出典の版や転載。版数を独立記事数と同一視しない。
- 内容の種類（例: 調教評価、陣営コメント、予想/展望、出走表/オッズ、結果/払戻、回顧、無関係）。調査用の区分であり、DBへ新分類ラベルを追加しない。単に馬名・着順が並ぶ記事と、その馬の状態や能力を文章で語る記事を区別する。結果記事にも将来のレースに使える文章がある。
- レース別の関連数、全文unitのみ/部分unitあり/関連なし、馬だけ/レースだけ/馬×レース、phase=pre/post/mixed/unknown、NULL/ラベル。馬×レースの関係が付かないsave_slices由来の部分unitがレースID指定の抽出でどう扱われるかをSQLで確認。
- 既報の110/487等を同じ定義・時点で再計算可能なら照合。これは範囲の充足であって分類精度ではない。未同定・不明を一律誤りと数えない。

### 4.2 取得元→保存本文の照合

過去のfetch_page/search応答とsave_article引数、DBの実bodyを対応付ける。取得時の本文が得られれば通常コードで厳密比較（hash、完全一致、連続部分文字列、許容する改行/空白の違い）。意味比較で逐語一致を代替しない。複数抜粋を連結した場合、元に存在する各範囲と連結の実態を区別する。LLMによる要約・言い換え・補足・異なる馬の文章の混入、title/dateの推測、引用の欠落などを調べる。証拠がない場合は判定不能とする。

取得側の問題（文字化け、JS主体、広告/ナビゲーション/目次、末尾8000文字打切り、HTTPエラー/partial）、LLMの抽出/保存の問題、DBの機械的保存の問題を分ける。fetch_pageがtruncated=falseでもHTMLの意味上の全文取得を保証しない。body_kind=fullと部分取得の矛盾も確認。原文を保存できない出典の扱いは既存契約に従い、原文の有無だけを品質の唯一の尺度にしない。

## 5. 分類の独立評価・馬別の文章範囲

全件概要から詳細対象を選び、Codexが先に本文を読み、妥当な対象馬・対象レース・前後区分・意味のある原文範囲を独立に判断した上でDBの実targetと照合する。同じモデルの自己申告やDBに保存されたphaseを正解としない。

詳細サンプルは12記事前後を目安に、A/B/B2/B3、事前/事後、単一馬/複数馬、見出し・コメント集・一般記事、全文/部分、正常/疑わしい例を含める。B3を十分含める（4版程度以上を目安）。下記§6の指定URL、および実際のS4対象（既報 ff1acfb9、13c4d030、完全IDを照合）を保存済みであれば必須対象にする。判断に必要な場合は追加する。恣意的な成功例だけの選定は避け、選定理由・評価対象数を記録。56版すべての馬×記事487組を厳密な正解作りのために再分類することは要求しない。

| 評価軸 | 判断 |
|---|---|
| 馬の関連付け | 馬名の登場だけ/その馬についての意味のある記述/比較・間接参照を区別。別馬誤同定、過剰付与・見落としを実例で確認 |
| レースの関連付け | 現在の対象と過去走の言及を区別。複数レースとの関係は適切なら許容。日付・ID不明は保留可 |
| phase | **関連付けたレースに対して**事前/事後を判定。記事の主題・文脈を用い、日付は補助。不明/混在を許容。記事に過去走の記述があるだけで現在のレースのpostにしない |
| 範囲の内容 | 馬名のみ、無関係な文、必要な文脈の欠落、他馬記述の混入、妥当な意味範囲、全文で十分な単一馬記事を区別 |
| 同定・保存の整合 | 原文hash/範囲/UUID/FKと意味の正しさを区別。逐語一致しても意味的に誤ることがある |

概ね妥当、明確な誤り、判断保留/不足を区別し、分母・判定根拠を記録する。詳細サンプルについて可能な範囲で誤付与・欠落と例示（原文の位置・ID・要約で示す）を報告。全体の代表性を断定しない。分類100%や全馬90%部分引用を合格条件にしない。量を重視し、不確実な情報も残す当初方針を維持する。新たな品質スコア・話者分類・厳密な時点証明を要求しない。研究上使える部分と、明確に改善が必要な部分を区別する。

## 6. 指定URLの重点調査 — 構造的な記事の処理

対象: https://agyo-keiba.com/nakayomakinpai2026-oikiri/ （公開ページでは2026-01-02、馬名14見出しの追い切り評価記事。目次にも馬名が現れる）。この数は公開ページの観察値で、DB保存本文が14頭分を含むとは限らない。

1. 通常DBに当該URL・同一記事の別版があるか、取得時刻・source_url/final_url・body_kind・本文文字数・hash・対象runを確認。存在しなければ「未保存」と記録し、既存記事の同形式の例も選ぶ。現在ページから取得し直してDBの旧保存内容とみなさない。
2. 取得ログがあれば、元ページの構造（目次、馬見出し、各本文、評価行、関連記事）と、実fetch応答、実DB本文を比較。構造の喪失、末尾欠落、改行、文字化け、不要部分、LLMの改変を切り分ける。各馬について実際に意味ある記述が保存されているか、単に名前があるだけかを確認。14頭分の表を作る（馬名、本文有無、見出し/段落の識別可否、登録された馬・race・phase、範囲の妥当性、欠落/余分）。保存されていない馬の本文を創作しない。
3. **文字位置の計算をLLMにさせる必要があるかを検証する。** 保存本文のコピーを用い、Codexが見出し/段落や意味から区切りを選ぶ。Python等で機械的に位置を算出し、逐語一致、出現回数、範囲、文字数を確認。目次中の馬名だけを見出しとして採らず、関連記事や隣の馬の範囲を混ぜない。既存の save_targets の quote（最大1024文字、完全一致・一意ならbody.find、自動位置解決）で表現可能かを、実装に従いオフラインで確認。曖昧な短い引用や長い範囲の扱いも確認する。必要なら引用と範囲の対応を一時ファイルで試算するが、本番/試験DBへの登録も新ツールの実装もしない。
4. 同種記事（全馬コメント集等）1〜2例と、構造のない複数馬記事、単一馬記事も対照に、同じやり方がどこまで通用するか確認。単一馬の本文全体で十分な場合に部分範囲を強制しない。既存本文の情報を使って、LLMが意味判断すべきところと通常コードで処理できるところを分ける。
5. 現行fetch_pageの soup.get_text("\\n", strip=True) は見出し/表のタグ情報を失い、本文最大8000文字。実データでこのことが問題になっているかを確認する。改善案として見出し・段落・表を保つ抽出等は候補に留め、必要性とデメリット（既存クライアント、原文位置、本文長、既存データとの整合）を報告する。媒体ごと専用parserの作成や共用サービス変更は行わない。

## 7. 過去セッションの原因分析・次のSkill研究への入力
