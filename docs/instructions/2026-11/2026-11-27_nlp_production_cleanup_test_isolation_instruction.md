## 1. 今回の依頼と停止位置

ユーザーは、研究・試験・検証中のデータを本番DBから除去し、検証用の領域で収集とDashboard表示を確認してから本番へ切り替えることを指示した。カバー率調査は終了する。現在の目的は本人による記事の私的な複製・保存・閲覧・整理であり、収集データを使うモデル作成は未定である。

今回実施するのは、本番に混在した研究・試験データの退避と除去、検証用保存先の分離、同じ実装を使う限定動作確認、私的利用を前提にした内部保存方針の修正まで。本番の初期全名簿処理・毎朝Cron・常駐解釈は停止を維持する。検証が通っても本番運転を自動で開始しない。結果を示し、ユーザーが切替・開始を指定した後に、その対象だけを動かす。

この指示は、前の[サーバ実装指示](2026-11-26_nlp_server_runtime_dashboard_instruction.md)の通常DBへの研究データ移行、通常保存先での有限試験、開始前のカバー率調査に関する扱いを置き換える。過去レポートは当時の記録として保管し、過去の指示を現在の本番書込み許可にしない。

本書の作成時点でVM15の清掃は未実施。このChatGPT環境から管理先への接続は Network is unreachable だった。以下は実機に接続できる担当者が実施する指示であり、完了報告ではない。

## 2. 対象と既存の状態

実機で現時点の状態を確認してから作業する。リポジトリで確認できる管理先は nlp@192.168.0.14、通常DBは keiba_nlp、DashboardはLAN内TCP8786。

[11月27日の実施報告](../../reports/2026-11/2026-11-27_nlp_server_runtime_dashboard_report.md)では、通常DBの新コーパスは1,303 URL・1,304版。過去研究599 URLと今回の有限試験・調査704 URLが同居し、解釈・試験計画・失敗試験も保存されている。

旧publicスキーマの56記事等も、[段階3Cの引き継ぎ](../../handoffs/2026-11/2026-11-26_stage3c_redesign_handover.md)にある試行の成果である。新collectionだけを清掃して旧試験データを本番のlegacy表示に残す処置では、今回の依頼を満たさない。

主な確認対象：

- collectionの本文、取得、解釈、観測、計画、作業キュー、過去の試験状態。
- publicの旧試験記事、原文範囲、馬・競走との対応、試験実行履歴、派生データ。
- /srv/nlp/runtime/dataの本文JSON、解釈、取得ID、観測、再利用・再開情報。
- /srv/nlp/hermesと研究プロファイルのCron、セッション、Memory、対象・取得IDを持つ状態。
- 通常MCP、旧mcp-nlpdb、Dashboard、解釈ワーカーの接続先と資格情報。

記事内容の良し悪しを1件ずつ審査して本番に残す作業は行わない。由来が研究・試験である一式を検証側へ保全し、本番は空の利用データ状態へ戻す。現物に今回の対象と明らかに異なる正式データが増えていた場合だけ、その対象を特定して報告する。v3や他のDB・サービスは対象外。

## 3. まず退避して、本番の利用データを空にする

1. NLPの書込み処理を停止・未起動の状態に揃える。対象のCron、実行中計画、常駐解釈、手動セッションからの書込みを確認する。DBや無関係なサービスを止める必要はない。
2. 現在のNLP DB、関連する永続ファイル、Hermesプロファイル・設定を組として私有領域へ退避する。記事本文・DBダンプ・秘密はGitへ入れない。
3. 検証用DBと検証用ファイル領域へ復元し、本文・解釈・必要な履歴が読めることと主要な件数を確認する。既存のバックアップ・復元手順を活用する。
4. 退避を確認してから、本番の研究・試験データを除去する。記事、解釈、試験由来の対象対応、観測、実行履歴、未処理キューが対象。スキーマ、拡張、必要な設定やコードは維持する。
5. 本番用の永続データディレクトリも新しい状態にする。旧本文・解釈・再開位置を通常の再取込経路に残さない。必要な静的設定・Skillと、入力として使う過去馬名名簿は、試験履歴と分けて配置する。
6. 本番の記事・解釈・試験計画・作業キューが空であり、旧資料表示や未解釈ワーカーからも試験記事へ到達しないことを確認する。現在の接続状態など、本来必要な稼働情報は別としてよい。

現在のDB一式を検証用として退避し、同じスキーマの空の本番DBを用意する方法でもよい。実機の構成に合う、戻せる単純な方法を選ぶ。DB名だけを変える場合も、接続中の処理・所有者・接続権限・既存名との衝突を確認する。

この退避・清掃は今回のユーザー依頼の中心であり、既存の研究データ保全ルールを理由に再承認待ちにしない。保全は検証領域とバックアップで行い、本番に残すことで代替しない。

## 4. 本番と検証を保存先から分離する

同じVM・PostgreSQLを使ってよく、新VMや新しい分散基盤は不要。基本は別DB、別の永続ファイル、別のHermes実行状態とする。試験用ロールが本番に書けない接続権限にする。本番の名前を既定値として黙って補う挙動を避ける。

本番と検証で共通にするものは、コード、Skill、モデル条件、MCP、収集・解釈の処理経路。変えるものは、DB接続先・資格情報、永続ファイル、Hermesのプロファイル・Cron・履歴、閲覧の接続先、試験対象と終了条件である。専用の簡略版収集器で検証を代用しない。

現行実装では以下を修正する。

- corpus.connect()の通常DB固定を解消し、保存先を明示する。
- 通常収集MCPだけでなく、旧mcp-nlpdbのNLP_DATABASE、Dashboard、独立解釈、各CLI、再取込処理の接続先も揃える。
- reviewという計画区分やDashboardでの非表示を、保存先の分離の代わりにしない。
- research.pyはROOTが/var/lib/keibaであることもDB保存の条件にしている。試験時だけROOTを変えてDB保存されなくなる別動作を作らない。ホスト側の領域を分け、各コンテナ内では同じパスへmountする方法等でよい。
- DBを空にしても旧JSONの再import、既知URL判定、解釈待ち選択、Cronの再開で試験データが戻らないよう、状態の参照先を分離する。
- 試験中のSkill変更は検証側に保存する。採用するSkill・コード・設定だけを後の本番切替対象にする。

本番Dashboardは0件・運用開始待ちを表示できればよい。検証Dashboardは検証用であることが明瞭な表示と接続先にし、退避した実記事や今後の試験結果を読めるようにする。管理ボタンや環境切替の管理画面は追加しない。

## 5. 現在の私的利用に合わせて保存方針を直す

現在の用途は、ユーザー本人が記事を私的に複製・保存し、Local LLMを補助に閲覧・検索・整理すること。モデル学習、データ販売、第三者への本文提供、商用サービスを現段階の目的として仮定しない。将来のモデル作成は未定であり、その可能性を現在の収集除外の根拠にしない。

利用条件の扱いは次の方針にする。

- 一般的な著作権表示や無断転載禁止から、本人の私的な保存まで自動的に禁止と推論しない。私的複製を認める記載も含めて読む。
- AIが本人の作業を補助することだけを理由に、無差別な大量取得やオッズの機械的収集と同一視しない。botという呼称や内部の自認を一律除外の理由にしない。
- 明示的な条件を扱うときは、現在の操作のどれに、どの記述が関係するかを示す。私的複製、閲覧、学習、第三者への転載を混同しない。条項の記載と、その適用・法的評価を同一視しない。
- スポニチ競馬Web・競馬ラボのコード内links_onlyと、私有collection-policy.jsonの追加設定を現在の目的で見直す。「以前からそうしていた」「AIだから」という理由だけの内部除外は解除する。現在の操作に関する明示条件が確認できる例は、その具体的な論点だけを短く示す。
- NLP側の独自robots事前拒否は撤廃を維持する。外部ツールの実際の制約やHTTP応答は内部設定と別に扱う。429等に応じた待機、認証・有料部分等の実際の制限への対応は通常の取得動作として扱う。
- 媒体ごとの同じ判断を記事ごとに繰り返す承認工程は追加しない。一媒体の未解決事項を全収集の停止理由にしない。

文化庁FAQ 6－⑲には、RAG等に伴う複製でも、個人の私的使用なら著作権法30条の適用が考えられるという説明がある。現在の目的を扱う際の参考にする。「AIを使うから私的複製ではない」という一律判断は採らない。一方、この説明だけから全サイトの個別条件が無関係になると断定するものでもない。

## 6. 検証側で同じ実装を確認する

カバー率の再計算、標本の追加、クラス・年代別の発見率調査は行わない。過去のカバー率報告は履歴であり、開始条件や改善目標として使わない。

検証用の保存先が分離された後、対象と終了条件を先に決めた少数の実例で、以下を確認する。

1. 本番用と同じ起点・MCP・Skill・保存処理を通し、開発PCから候補URLを手渡さずサーバだけで記事を取得する。日次と過去記事で必要な経路は区別する。
2. 取得原文が検証DBへ入り、独立LLM解釈の結果が原文とは別に保存される。意味は概ね役立てばよく、全件の厳密な正解判定は要求しない。
3. 検証Dashboardで検索、原文、解釈、出典、件数、処理状況を確認する。閲覧自体が収集や推論を起動しない。
4. 試験後も本番の記事・解釈・試験計画・キューが空であること、試験用予定が終わっていることを確認する。

9割程度でよいという自然言語の方針、Local LLMの解釈に数日程度かけてよい方針は維持する。試験データと本番データの混在は、意味の曖昧さとは別の実装上の問題として直す。

## 7. 切替と完了報告

今回の終了位置は、本番清掃・検証領域分離・限定動作確認を終え、本番の収集と解釈を停止している状態。

将来の切替では検証済みコード・Skill・設定を本番の保存先で使う。検証DB、試験履歴、テスト用Cron、試験の処理済み位置を本番へ丸ごと戻さない。研究記事の本番への再取込も自動では行わない。

完了報告には次だけを明確に示す。

- 本番から外したデータの範囲、退避先、清掃前後の件数。
- 本番と検証のDB・永続領域・プロファイル・Dashboardの対応。
- 同じ実装で確認した取得・解釈・表示と、本番に試験データが増えなかった結果。
- 変更した内部保存制限と、残る具体的な媒体条件があればその根拠。
- 本番の初期全名簿・毎朝Cron・常駐解釈の停止状態と、今回動いた試験の終了。
- 変更commit、実機配備版、未実施事項。

共通規約、Hermes用規約、Skill内の複製規約、媒体別の手引き、READMEを実際の配置と最新方針に揃える。過去の数値レポートは書き換えて成功扱いせず、必要なら現在の方針から外れた履歴であることを注記する。
