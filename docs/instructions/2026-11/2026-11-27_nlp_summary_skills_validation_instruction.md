# 改訂Skillの配備・馬別要約・解釈時間の比較検証（Codex向け）

日付：2026-11-27 JST。文書作成時の基準は `ff43ac3ccfef90677db24615c8da87ff1930b1af`。

## 1. 目的と担当

ユーザーは、Skillを改訂して、要約の粒度が適切になるか、解釈時間が短くなるかを実機で確認したい。既存の解釈結果は破棄してよい。原記事はそのまま使う。

ChatGPTは今回、関連するSkill・作業規約などのMarkdownと本指示書を改訂する。**コード変更、VM15への配備、DB整理、実モデルを使う検証はCodexが本指示書に基づいて行う。** 指示の範囲内で手順や補助コードを選び、実例からSkillを調整してよい。説明・設計相談だけを根拠に、未依頼の実装や次工程の開始を追加しない。

成果物は、改訂Skillによる少数の実記事の新要約、同じ記事・モデル設定での旧新比較、検証Dashboardで読める新結果、実施レポートである。今回の完了報告後に全保存記事の処理が続く状態にはしない。

## 2. 維持する方針と今回の範囲

- 自然言語は曖昧でよい。分類・収集は「9割がた役立てば十分」という実用性の目安であり、統計的な90%達成証明ではない。全件の意味検査、厳密な馬ID照合、カバー率調査を追加しない。
- 原文を広く蓄積する方針を維持する。要約対象の選び方を記事収集の入口フィルタにしない。今回は保存済み記事だけで試し、新規収集・媒体研究は行わない。
- 検証DB `keiba_nlp_trial`、検証領域・Hermesプロファイルを使う。本番DB `keiba_nlp`、v3、他の利用者のモデル設定・処理には触れない。本番の全名簿、毎朝Cron、常駐解釈は開始待ちを維持する。
- 1記事3〜4分というだけで不合格にしない。専用Local LLMの初期処理に日数がかかることは許容されている。今回は短縮の有無と内容の変化を測り、速度だけでモデル・Thinkingを弱めたり、記事を削ったりしない。
- 閲覧画面は既存Dashboardを使う。新たな管理画面、Cron編集画面、恒久的な評価基盤は作らない。必要なコード修正は、配備・明示記事の有限実行・計測・旧結果の整理・表示に必要な範囲にとどめる。

## 3. 要約の意味を揃える

### 単位は「1記事・独立して説明されている馬ごとに1要約」

記事に登場した全馬を独立対象にせず、複数馬のコメント集を代表1頭へもまとめない。文章量や馬名の回数による固定基準は不要。記事の文脈をLLMが読めばよい。

| 記事の例 | 期待する扱い |
|---|---|
| カランダガンの記事で陣営が「マスカレードボールとの対決になる」と話す | カランダガンの要約に対戦への見方を含める。比較相手だけの独立要約は作らない |
| カランダガンの調教で、併せた馬を突き放したと書かれる | 併せ馬の名前が出ただけでは、その馬の独立要約を作らない |
| カランダガン、マスカレードボールなど各馬の追い切り・陣営談話を併記 | 各馬に一つずつ要約。見出しや登場順で代表を決めない |
| 同じ馬の調教師談・騎手談・追い切り時計が離れた箇所にある | 話者や条件を文章内に残し、同じ馬の一つの要約にまとめる |
| 「前走は太め残りだったが、今回は調教を積んで期待できる」 | 今回走に紐づく事前要約一つ。前走の別項目を作らず、mixedにもしない |
| 今回走の回顧に次走への希望が添えられる | 回顧の対象競走に対するpostの要約内に希望を残す。次走の別項目を必須にしない |

紐づける競走は、その馬について記事が主題にしている競走一つ。背景の過去走・対戦相手は自然文の中に残す。記事自体が過去の競走の回顧なら、その過去競走が対象になる。検索の起点になった競走を一律に付けない。主題が定まらない場合はnullやunknownでよい。

各馬の要約を競走全体の項目へ重複して書かない。馬に属さない独立した馬場・展開の見解は、必要ならhorse=nullで残せる。原文を読めば普通に分かる内容を、発言・文・競走・時点ごとの細かな事実レコードへ展開することは目的ではない。

## 5. 改訂Skillと既存コードを配備する

対象は `keiba-interpret`、`keiba-search`、`keiba-coordinate` と、実機用規約・複製されたwork-rules。解釈本文の正本は今回改訂したSkillとし、親や検索担当から「全言及馬・全過去走を別項目へ」と要求が戻らないことを確認する。修正した3役のSkillすべてが独立解釈APIの入力に入るわけではない。実際に解釈へ渡されたsystem文面を確認する。

`ff43ac3` には馬別一覧 `/horses` と、自動対象選択でSkill変更だけによる全件やり直しを防ぐコードがある。これは前回ChatGPTがリポジトリへ反映したもので、実機未配備として報告されている。本指示に照らしてCodexが内容と実機状態を確認し、使える変更は再利用する。無条件に配備済み・検証済みとは扱わず、最初から作り直すことも要求しない。

既存配備処理がHermesの現地Skill修正を保護して新Skillを適用しなかった場合は、退避した旧内容と照合し、今回の方針を採用した実ファイルを確認する。必要な再起動は検証側を中心に、停止中の処理が意図せず再開しない手順で行う。共有コードの更新が必要なら本番の停止・保存先分離を維持する。

## 6. 同じ記事・同じ設定で、旧新の実生成を比較する

### 主比較

- **A：実機で使われていた旧解釈Skill。** 実機の控えを優先する。復元できずGitの過去版で代替する場合は、その差を明記する。
- **B：今回改訂した解釈Skill。** 子や配備先で再変更されていない実際の文面を記録する。

同じ取得IDの本文・掲載表示・取得観測日時を渡す。比較のために再取得して本文や日時を変えない。モデル、Thinking、reasoning effort、最大トークンなどは揃える。設定を勝手に弱めた結果を「Skillで短縮」と報告しない。

各記事を旧新1回ずつ実生成すれば、6件なら約12回になる。`fresh=True`相当の経路などで、**キャッシュ再利用ではなく実際に生成されたこと**を確認する。旧保存結果の所要秒は参考にできるが、キャッシュで返った秒数と新生成を比較しない。旧新の実行順や初回ロード・他処理との競合が大きく違えば、その例だけ補足すればよい。多数回反復や統計的有意差の証明は不要。

**`operations.finite(Aの収集計画, Bの収集計画)` を比較用に起動しない。** この経路は元の2試行に属する全保存版を登録する。固定した取得IDの明示リストで別の有限実行を作り、既存2,438版のキューは再開・初期化しない。Skillや旧結果の変更で自動対象が増えても、今回の対象リストを広げない。

### 必要な場合だけ行う切り分け

新Skillでも想定より重い場合は、同じモデル設定・同じ保存本文で、同じ意味を求める短い通常会話風の依頼を少数だけ比較してよい。対象が同じ馬数・同じ内容量になるようにし、一頭だけの短い回答を全馬の構造化要約と同列に速度比較しない。これは原因を調べる補助比較として区別する。

モデルの差替え、Thinking無効化、reasoning effortや最大トークンの一律変更は今回の主比較に含めない。短縮しなかった場合は、その結果と内訳を報告すればよい。追加の設定比較が有用なら、その具体案を報告し、未実施と区別する。

### 最低限記録するもの

記事ごとにA/Bを並べ、取得ID・版ID、Skillのハッシュ、実設定、本文文字数、所要秒、出力項目数と対象馬、成功・失敗、`reused`、`finish_reason`、APIが返した`usage`を残す。入力・回答・思考トークンは返却された区分どおりに記録し、思考量が不明なら不明とする。長い思考本文を保存することは要求しない。

既存の`seconds`はモデル要求から応答解析までで、外側のロック待ち・最終保存・記事間のキュー処理を含まない。記事全体の経過時間と区別する。競合や待ちが疑われるときだけ追加の内訳を確認し、全体の遅さをDBやThinkingのどちらかと推測で断定しない。現在取得できる計測値を優先し、新しい監視基盤を必須にしない。

## 7. 内容を読み、旧解釈を整理してDashboardで確認する

少数の実例を原文と並べて読み、第3節の要約単位・対象馬・主題の競走が概ね実現できたかを判断する。複数馬の談話を代表1頭へ混ぜる、比較相手を独立対象へ増やす、背景の過去走へ分割する、といった繰り返す傾向を優先して直す。小さな表現差や曖昧な境界を全件審査へ広げない。必要なSkill調整後は、その変更が効く例だけ追加で確認する。

ユーザーは既存解釈の破棄を許可している。必要な比較記録と今回採用する新結果を確保したら、**検証DBの旧interpretations行と、対応する検証領域のinterpretations/*.jsonを揃えて整理し、通常閲覧は今回の新要約を読める状態にする。** Aの再生成結果も比較記録として控え、通常閲覧へ新旧が混ざらないようにする。削除対象IDと保持する新結果IDを分けて確認し、本文・versions・captures・収集履歴・計画・キューを一括削除しない。

DBだけ残してJSONを消すと再利用で読込失敗が起こり得る。JSONだけ残すと再取込で旧解釈が戻り得る。既存の解釈計画の完了履歴は、現在残っている有効な解釈数とは区別し、必要なら停止理由・旧結果整理の注記を残す。削除された解釈を埋めるために全キューを初期化・再開しない。

検証Dashboardでは、カランダガンなどの馬名検索から新しい一つの要約を読み、複数馬の記事では各馬を個別に探せること、原文と出典へ戻れることを確認する。既存の分割文をカード内に並べただけの表示と、新Skillで新しく生成した一つの要約を区別する。既存原文の大半が未解釈と表示されても、この限定検証の終了状態として正常。

## 8. 終了状態と報告

指定した少数例の比較と表示確認が終わったら、今回の比較用処理を終了する。旧有限キューも停止のままにする。検証Dashboardと保存原文、新要約は閲覧できるよう残し、本番・新規収集・毎朝Cron・全名簿・全保存版の再解釈は起動しない。

レポートは `docs/reports/2026-11/2026-11-27_nlp_summary_skills_validation_report.md` を目安に保存し、最終Skill・必要なコード・文書を対象ファイルだけcommit/pushしてリモート反映を確認する。実記事の全文、旧新出力の全文、秘密、DB実体はGit外の検証領域に置く。

報告には次を含める。

1. **結論**：要約の単位がどう変わり、解釈時間が短縮・同程度・悪化のどれだったか。改善しなかった結果もそのまま示す。
2. **記事別の旧新比較表**：所要秒、利用可能なトークン内訳、項目数・要約対象馬、主要な内容の差。少数例の中央値や範囲を添えてよいが、全体性能へ一般化しない。
3. **読める実例**：単独馬・複数馬の新要約へ進める検証Dashboardリンク。項目数が減ったことだけを品質改善とせず、対象馬や理由・条件を落としていないかを示す。
4. **データ整理**：旧解釈の整理件数、保持した新結果、原文・取得記録の保持、比較記録の再開先。旧キューと今回の実行状態を区別する。
5. **配備と終了**：Git版・実機版・実際に使ったSkillと設定、変更したコードの範囲、稼働中処理と次回予定。本番の停止・空状態を確認し、未確認があればそう記す。
6. **残る論点**：まだ時間が長ければ、思考量・回答量・モデル待ちなど確認できた内訳と、次に試す価値のある変更。測っていない原因を確定しない。

実機へ接続できない場合は、文面確認や他モデルの試行をLocal LLMでの検証成功として報告しない。到達できた範囲と残作業を明示する。
