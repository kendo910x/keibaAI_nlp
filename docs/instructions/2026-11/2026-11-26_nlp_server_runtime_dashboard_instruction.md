ユーザーの最新の整理により、日常的に使わない管理操作の画面は作らない。初期構築の起動、Cronの変更、設定・Skill・ツールの改修、復旧や再実行は、必要時にCodexへ依頼し、CLI・設定ファイルで行う。以前の案にあった「収集計画」画面、開始・停止・再開ボタン、Cron編集画面は今回の範囲から外す。

## 3. 維持する品質方針と作業範囲

### 3.1 自然言語の扱い

- 分類・収集は「9割がた当たれば十分」。統計的な90%達成証明、重大な意味誤りゼロ、全記事の意味検査、外部IDの全件照合を要求しない。
- 日時不明、対象が曖昧、平凡・否定的・相反する情報も保存する。有用性や確信度を入口の厳しいフィルタにしない。
- 馬名名簿は探索の手掛かりであり、保存対象の許可リストではない。見つからない馬は未発見として次へ進み、全馬に同走馬探索を義務付けない。
- Local LLMによる初期データの解釈は数日〜1週間程度かかってよい。速度だけを理由にモデル・Thinkingを弱めたり、解釈対象を削ったりしない。
- NLP側の独自robots事前拒否は撤廃済み。外部ツール自身の制約、実際のHTTP応答、認証・公開範囲は区別して扱う。
- 取得原文はコードが直接保存し、LLMの解釈文と区別する。進捗・処理失敗・保存状態の管理は、意味を厳密に審査する仕組みにしない。

### 3.2 実施担当に依頼する範囲

既存NLP環境への通常実行用Skill・MCP・収集／解釈処理の配置、必要なNLP DBの変更と研究データの引き継ぎ、閲覧専用Dashboardの配備、初期構築用CLIと毎朝の定期収集の準備、有限の試験・再開確認、カバー率調査、運用手順とレビュー資料の作成まで行う。コードを書くだけでなく、実物を確認できる配置まで済ませる。

**毎朝の本運用Cronは未登録または無効、全名簿を対象にした初期構築は未起動、本作業で追加する常駐解釈ワーカーも停止の状態で引き渡す。** 試験・調査は対象と終了条件を事前に定めた有限の実行に限る。全名簿への自動拡張、全未処理記事への連続処理、試験終了から本運用への移行を起こさない。既存本文を使う限定的な解釈は試験として行ってよい。

Dashboard、DB、閲覧API等は確認のため稼働させてよい。収集・解釈の本運用が保留されていることと、閲覧サービスの稼働を区別する。試験で追加した予定・ジョブを整理し、再起動・再ログイン・日付の経過で保留中の本運用が始まらない設定にする。無関係な既存サービス・承認済みの別作業は停止しない。

通常運転は常時稼働するサーバ群で完結させる。既存Local LLM・共用検索が別サーバでもよい。開発PCのブラウザー操作、候補URLの手渡し、PC常駐の同期処理、Codexの次回指示を日常経路に残さない。

v3の既存DB・Live・購入系・Dashboard・サービスは変更しない。必要な名簿は既存の読み取り専用参照・エクスポート、または公開情報から得る。NLP既存データを保全し、必要なDB変更前にバックアップと戻し方を用意する。外部アカウント登録・課金・インターネットへの公開・新しい通知連携は今回に含めない。

本書を作成・commitする文書作業と、後続の実装担当が行うサーバ配備は別である。実装方法、少数の補助処理、試験対象、ポート等の通常の選択には裁量を持たせ、本書の範囲内で細かな再承認を求めない。**ユーザーによるSkill・調査結果の確認後の開始指示だけは、実装完了や試験成功で代替しない。** 初期構築・日常収集・常駐解釈のどれを開始するかも、その指示の範囲に従う。

## 4. 実装する三つの処理と今回の停止位置

| 処理 | 開始指示後の運用 | 今回の引き渡し状態 |
|---|---|---|
| 過去記事の初期構築 | CLIから既存v3由来の名簿を使う有限の計画を開始・再開 | 実装・有限試験済み。全名簿の計画は未起動 |
| 毎朝の収集 | Hermes Cronから毎朝1回、当週・直近の対象と新着を確認 | 設定案と起動経路を検証。本運用の予定は未登録または無効 |
| 記事解釈 | 保存済みの未処理記事を、収集と分けてサーバで順次処理 | 有限の解釈試験済み。常駐処理は停止し、残件を自動消化しない |

以下の各節は開始後に実現する動作を定める。今回の実装担当に、本格収集・全件解釈の起動を指示するものではない。

### 4.1 過去記事の初期構築

開始時に名簿と活動期間を固定し、探索済みの馬・年月・一覧の位置をサーバへ保存する。既存名簿をそのまま再利用できるなら、再抽出やv3全DB同期を先行条件にしない。馬名・活動年から探す方法と、媒体の月別・カテゴリ一覧をまとめて読む方法を併用する。

CLIから開始・状態確認・区切りでの停止・再開ができるようにする。コマンド名や内部の処理単位は担当者が選んでよい。一回の計画を複数のセッションや処理に分け、接続端末やCodexのセッションを閉じても継続する。完了は、指定範囲を合理的に一巡した意味とし、全馬の記事発見・Web全体の網羅を意味しない。

後から媒体や対象期間を追加するときに、必要な範囲をCLIで追加実行できればよい。初期構築用の管理画面は作らない。

### 4.2 毎朝の収集

初版は**毎朝1回の同じ処理**にする。登録公表後・出馬表公表後・開催日夕方などの別Cronを先に増やさない。具体的な時刻は既存運用との関係を確認して実装担当がJSTで提案し、未有効の設定案とレポートへ明記する。開始指示までは予定を動かさない。後日の変更はCodex依頼で行う。

1. 当週と直近の開催、現在取得できる登録馬・出馬表・結果を確認する。
2. 前回から増えた対象や更新情報を取り込み、検索用の名簿を補充する。
3. 複数の主要媒体の新着・一覧と、対象馬・競走を手掛かりに記事を探す。一般競走や名簿外の情報も扱う。
4. 本文を保存し、既知のものを再利用しながら、未解釈記事を後続処理へ渡す。
5. 保存件数・未発見・失敗・残件と再開位置を記録して今回の実行を終える。

朝の実行後に公表された情報を次の朝に拾う運転を許容する。出馬表がまだない場合は、使える登録・予定情報と新着一覧で進み、次回に更新を確認する。最新対象を毎回PCで作る手順にしない。

通常コードは差分・既知記事・取得状態を扱い、Hermesは探索先・追加検索・切り上げを選ぶ。大量の過去名簿を毎朝読み直して同じ全件検索を繰り返さない。既知URLを永久に無視せず、追記・訂正がありそうな記事は必要に応じて再訪し、内容が同じなら再利用する。

### 4.3 記事単位の独立解釈

既存の独立推論と再利用処理を活用し、未処理記事を継続して解釈・保存する。失敗した記事は状態を残し、ほかの記事へ進める。未解釈の蓄積を、それだけで異常扱いしない。日常の新着収集を優先し、過去の大量処理は区切りで順番を譲れるようにする。速度の合格値は設けない。

**取得済みの掲載日・更新日の表示を、本文とともに補助文脈として渡す。** 現行の `interpret()` は本文のみを渡すため、別保存した `published_label` が使われていない。更新を初回掲載と断定せず、取得日時と記事自身の日時を区別し、不明でも処理する。検索の出発点の馬やレースを、記事が述べる対象として強制しない。入力を変更した場合は再利用判定にも反映し、旧入力の結果を新入力で処理済みと誤認しない。

## 5. サーバ配置・ツール・永続保存

### 5.1 通常実行への組み込み

研究プロファイルで実証したSkill・取得コード・MCPを、常用する配置と設定へ組み込む。古い `work-rules.md` 等の複製も更新し、厳密さ・時間・robotsの旧条件を復活させない。Skillの改善履歴を残し、次のセッションから利用できるようにする。利用者からの設定・Skill変更依頼はCodexが扱い、Hermesが許可された探索の経験からSkillを改善する裁量も維持する。Skillの改善を、Cronやモデル設定等の無断変更へ広げない。

定期起動は既存Hermes Cronを使う。gateway／ticker、Cron用のMCP・Skill・作業ディレクトリを確認する。CLI用toolsetの設定だけでCronにも同じツールが渡ると仮定しない。毎回新しいセッションでも、サーバ上の進捗を読んで続けられるようにする。有限の試験用起動と本運用の予定を区別し、本運用は未登録または無効の状態を保つ。開始後の常駐・再起動後復帰は実装するが、現段階で自動起動を有効にしない。

実装時は導入済みの固定版と実機を基準にする。公式資料は[固定版のCron](https://github.com/NousResearch/hermes-agent/blob/d923a5eb487a17c0a68801bba9ef0f56c81040a8/website/docs/user-guide/features/cron.md)を参照。新しいHermesへの更新や独自スケジューラーの新設を前提にしない。

必要なブラウザー操作はサーバへ配置するか、サーバだけで使える別の導線で目的を満たす。現在の `listing(render=true)` は汎用クリック操作ではないため、必要箇所だけ既存Playwright等と小さな補助を使って補う。PCで候補を作って渡す運用を残して自律運転完了にしない。

同じ作業の重複起動と、別処理同士のLocal LLMの取り合いを避けるため、既存の実行制御を使い、必要な範囲で並行数と優先順位を設定する。独自の分散ジョブ基盤を先に作らない。

### 5.2 データと進捗

既存のPostgreSQLとサーバの永続領域を活かし、原文版・独立した解釈文・対象・実行状況を保存して読み出せるようにする。研究用の私有ファイルだけに成果を置いたままで終了しない。必要な表・列・APIの数は先に固定せず、実物に合う最小限の変更を選ぶ。

現行の[DB定義](../../../infra/nlp-vm/db/migrations/001_initial.sql)の `text_units` は原文範囲のモデルなので、生成文を原文本文へ上書きしたり、架空の文字位置で表現したりしない。正規化した馬名、分かっている開催日・競馬場・R番号による識別を使い、不明・未解決も保持する。外部ID照合を全記事の保存条件にしない。

研究データの本文・既存解釈・名簿・必要な再開情報を引き継ぎ、元の取得ID・版との対応と件数を確認する。基準値から増減があれば説明する。既存通常DBの旧資料は保全し、取得原文の品質が確認された新コーパスと無条件に同じものとして扱わない。これは意味の全件検査を要求するものではない。

再開に必要な未処理・処理済み・失敗と位置を永続保存する。進捗の正本をCodexの会話や開発PCのhandoffに置かない。サービス停止・新しいセッション・端末切断後も保存データから続行できるようにする。保存先、容量の確認方法、バックアップと復元方法を既存運用に合わせて具体化する。

既存の `links_only` と私有 `collection-policy.json` は、媒体側の明示条件・内部の保存設定・実際の取得失敗を区別して引き継ぐ。由来不明の設定を根拠なく恒久的な媒体除外へ拡張しない。未解決の媒体に固執せず、利用できる導線で収集を続ける。媒体全体の再調査を配備の前提にしない。

## 6. 閲覧専用Dashboard

NLPサーバ上で提供する、小さな独立Webアプリを基本とする。既存Hermesの状態取得機能・CLI・API・履歴は再利用してよい。Hermes標準Dashboardの導入・公開を必須にせず、任意の詳細確認先として扱う。v3 Dashboardへ機能を追加しない。

利用者はブラウザーから状態とデータを読む。開始後のサーバ処理はブラウザーを閉じても続くが、今回の引き渡し時は収集・解釈の本運用を保留する。LAN内の既存運用に合う接続方法を選び、接続先を報告する。画面の検索・表示・集計は通常のDB検索で行い、閲覧のたびにLLM推論を起動しない。

### 6.1 稼働状況・処理結果

初版で表示する内容は以下。

| 区分 | 表示内容 |
|---|---|
| 定期実行 | 未登録・無効・有効、スケジューラーの状態、直近の確認時刻、実際の次回予定（JST）。保留中は次回予定なし |
| 接続状態 | DB、Local LLM、取得・検索経路等の稼働または直近の確認結果。古い結果には確認時刻を表示 |
| 現在の処理 | 待機・収集・解釈等の状態、開始時刻、現在の対象、最終進捗時刻 |
| 前回・最近の実行 | 開始／終了、正常終了・一部失敗・失敗・実行中などの状態、要点と必要な詳細記録 |
| 処理件数 | 新規保存、既知再利用、取得失敗、解釈完了等。実行結果とDB全体の件数を区別 |
| 初期構築・解釈 | 探索済み範囲／名簿の対象数、未発見、保存数、解釈済み・未処理 |
| 対応が必要な問題 | 継続できない理由と確認先。生の長い思考ログを通常画面へ並べない |

プロセスが存在するだけで仕事の成功と判定しない。正常終了は、今回の処理を実施し、結果と進捗を保存して終了した意味とする。新着0件、個別馬の未発見、単一ページの失敗、長いLLM処理、解釈待ちがあることを、一律に全体の異常へしない。DBや必要な取得・推論経路へ接続できず当該処理を進められなかった場合は、結果を書いたことだけで正常とせず、失敗または対応が必要な状態として示す。既知の障害は解消後の確認結果へ更新し、古い失敗を現在の障害のように表示し続けない。

名簿の探索済み割合は表示できるが、Web記事の網羅率や意味精度として表示しない。健康確認や画面更新のためにLLMへ回答を生成させる必要はない。

今回の引き渡しでは「実装済み・運用開始待ち」「本運用の次回予定なし」を表示できるようにする。意図的な保留を障害扱いせず、提案した時刻を有効な次回予定として表示しない。レビュー用の新しい管理画面や開始ボタンを追加する必要はない。

### 6.2 記事検索・閲覧・件数

- 馬名・競走・キーワード・媒体・期間から検索できる。未解釈でも本文の文字列検索で見つかるようにする。
- 一覧には見出し、媒体、掲載／更新の表示、取得日時、判明した対象、本文保存状態、解釈状態を示す。保存が新しい順と記事日時順を選べるようにする。
- 詳細では保存本文とLLMの解釈を分け、元記事URLと日時、対象、必要なら過去の保存版を読めるようにする。
- URL単位の記事数と保存版数、解釈済み・未処理数を分ける。媒体別・年代別の簡単な件数表示を用意する。日付不明も件数から消さない。
- 未解釈・日時不明・対象未確定・公開部分だけの記事も、保存された時点から表示する。URLのみの記録は本文のある記事と区別する。
- レースは分かっている開催日・競馬場・R番号と名称を使う。検索の出発点の馬と、本文が実際に述べる馬を混同しない。関連付けが未完でもキーワード検索と出典から読めるようにする。
- 同じURLの複数版や転載先を、独立した証言数と表示しない。精密な転載同定を閲覧開始の条件にはしない。

件数が増えても扱える一覧のページ分け等は、通常の実装として選ぶ。Embedding検索、予測表示、精度採点、任意SQL、記事の編集・削除、汎用チャットは初版に含めない。

### 6.3 管理操作は画面に作らない

初期構築の開始・停止・再開、Cronの作成・編集・有効／無効、Skill・モデル・設定の編集、手動収集・再解釈の実行ボタンは作らない。検索条件や並び順の変更は閲覧操作として提供する。設定変更・保守・復旧は、CodexがCLIと設定ファイルで行う。

## 7. 開始前に確認するSkillと記事の集まり方

### 7.1 完成したSkillをレビューできる形にする

検索・記事解釈・統括の各Skillについて、実際に配置した全文へのリンク、版、対応するツール・設定を報告する。「Skillを更新した」だけでは終えない。利用者が次を把握できる短い日本語の説明を添える。

- 過去の馬名名簿と、日常の登録馬・出馬表から、どの順序でどの媒体・導線を探すか。
- 馬名検索で見つからない場合の補完方法、探索を切り上げる目安、名簿外の情報の扱い。
- 通常コードが担う保存・再利用・進捗管理と、LLMが判断する探索・解釈の役割。
- 独立解釈へ渡す本文と日時等の文脈、出力例、曖昧さや未解決を残す方法。
- 親・子エージェントの分担、経験によるSkill更新、毎回の開始・終了・再開の動き。

調査には原則として配置予定のSkill・ツール・モデル条件を使い、代表的なケースをHermesがサーバ側だけで再現する。Codexが手作業で追加発見した分は分けて記録し、Hermesの到達実績へ混ぜない。途中の有効な改善は最終Skillへ取り込み、変更が発見量に影響した場合は該当する代表例を再確認する。全試行を細かな編集のたびにやり直す必要はない。

### 7.2 カバー率調査の目的と対象

ユーザーが知りたいのは、馬名を手掛かりに過去記事を探したときに、**重賞では出走馬の記事が一通り揃うのか、条件戦では有力馬を中心に揃うのか、ほとんど得られない区分があるのか**という量感である。全Web記事の母数は分からないので、ここでいうカバー率は、選定した出走馬について記事を発見・保存できた割合とする。将来の全名簿での最終値を断定しない。

対象は検索結果を見てから成功例だけ選ばず、v3の既存名簿・出走履歴や公開出馬表・結果から先に選ぶ。次の違いが見える組合せを作り、各選定レースは全出走馬を調べる。

- 重賞（G1とG2・G3の双方）、オープン・リステッド、1〜3勝クラス、未勝利・新馬。
- 直近、数年前（目安3〜5年前）、古い年代（目安8〜10年前）。開催・季節・媒体の一例だけに寄せない。
- 各レースの有力馬とそれ以外。過去レースでは当時の人気上位（例：1〜3番人気）を簡便な目安にできる。人気が不明なら未分類でよい。結果を見て記事の多い勝ち馬だけを「有力馬」にしない。分類方法は簡単に記す。

初めの規模は**10〜15競走、延べ150〜250頭程度**を目安とし、具体的な選定と増減は担当者に任せる。全区分×全年代の厳密な組合せ表や検定は不要で、判断しにくい区分だけ少し追加する。直近の例には日常運用を想定した事前・事後の探索も含め、古い記事の発掘と結果を分ける。馬名の活動期間全体の記事と当該競走の記事を混同しない。

過去名簿全体の粗い見通し用に、既存名簿から機械的に選ぶ**数十〜100頭程度**も補助標本とする。無作為抽出や固定間隔等の選び方を先に決め、知名度や発見済み記事で選ばない。競走標本と重なる馬の結果は再利用してよい。この標本では、その馬について何らかの記事が得られるかを主に見て、重賞を多めに含む競走標本の集計を全名簿のカバー率と取り違えない。

### 7.3 調べ方と数え方

馬名を起点とし、必要に応じて活動年や媒体を足す標準的な検索を試す。その後、サイト内の一覧・月別アーカイブ・競走名・同走馬等でどの程度補えるかを見る。全馬に同走馬探索を義務付けず、合理的な範囲で打ち切る。探索に使った手掛かりとおおよその回数・範囲を残し、簡単な馬名検索で得た分と、補完で増えた分が分かるようにする。発見率を上げるために未発見馬だけを際限なく探し続けない。

各レースの全出走馬を分母に、次を分けて集計する。横断集計では延べ出走馬数と実際の馬数を区別する。

| 観点 | 知りたいこと |
|---|---|
| 馬についての記事 | 活動期間内に、その馬への言及を含む記事が少なくとも一つ見つかるか |
| 当該競走の事前記事 | そのレースに向けた調教、関係者談、展望等があるか |
| 当該競走の事後記事 | そのレースの騎手談、回顧、敗因、次走等があるか |
| 記述の厚み | 名前や結果の列挙だけか、馬についての短いコメント・見解等もあるか |
| 記事の量 | 馬ごとの0件・1件・複数件の分布、中央値とおおよその幅、URL数と主要媒体の内訳 |
| 到達と保存の差 | 候補発見、公開本文・公開部分の保存、URLのみ・取得不能、未発見の違い |

本文の一つに複数馬のコメントがあれば、言及された各馬のカバーへ数えてよい。ただし全体の保存記事数は重複を除き、一つの記事を馬数分の別記事としない。同一URLの保存版や明らかな転載も、量の説明で区別する。名前の列挙だけの資料も保存し、報告では内容のある記述と別に見せる。

関連する競走、事前・事後、記述の厚みはLLMが文脈から大まかに判断してよい。掲載日等の手掛かりがあれば使うが、厳密な時点証明を全件へ要求しない。不明は不明として残す。後年の一般記事を、当時の当該レースの事前記事として数えない。

### 7.4 開始判断に使える報告

クラス・年代・有力馬／その他の単純な表で、調査対象数、記事のある馬数・割合、事前／事後の数、馬ごとの記事量を示す。割合だけでなく分子・分母を併記する。数例の本文・解釈・出典と、未発見・名前の列挙だけだった例をDashboardまたはレポートから読めるようにする。

「この標本では重賞の事後談は広く得られたが、古い条件戦の事前情報は薄い」といった、観測した範囲の説明を行う。馬名検索だけの場合と補完後の差、媒体への偏り、探索を増やしても伸びにくかった部分を示す。名簿から選んだ補助標本の結果は競走別の集計と分けて示す。全名簿へ広げた際のカバー率・保存量は、根拠がある範囲で粗い見通しと限界を示せばよく、標本のURL数を機械的に54,591頭へ掛けない。

**「分類・収集は9割程度で十分」という意味精度の方針を、記事カバー率90%の合格条件に変えない。** カバー率が低い結果も判断材料であり、合格値へ達するまで調査や精密な照合を繰り返さない。今回の報告をユーザーが読んだうえで、開始する処理・探索の優先順位・必要な追加確認を決める。

## 8. 進め方と検証

### 8.1 実装と調査の順序

1. 現物のサーバ配置・研究データ・通常DB・固定Hermesを確認し、必要な保存変更と起動構成を短く整理する。
2. 原文・解釈・進捗を永続保存する経路を整え、既存研究データを引き継ぐ。
3. 記事一覧・詳細・件数と稼働状況を、実データで表示する。
4. 初期構築用CLI、毎朝のHermes Cron、未処理記事の解釈を実装する。必要なサーバ側の導線・名簿更新を整え、本運用は未有効にする。
5. 第7節の対象を選び、有限の探索・解釈・起動・再開試験とカバー率調査を行う。結果に応じてSkill・ツールを改善する。
6. 最終Skill・調査結果・実装状態をレビューできる形にまとめ、試験処理を終了する。本運用のCron・初期全名簿ジョブ・常駐解釈が動かない状態を確認して引き渡す。

工程は並行してよい。全記事の解釈、全媒体の取得、最終的な予測用途の決定を、実装・Dashboard配備の前提にしない。開始前レビューは実装を止めるためではなく、完成したものと収集量を見て運用を判断するために設ける。

### 8.2 必要十分な実機確認

次の観測を、代表的な実データと実行経路で確認する。

- **データの引き継ぎ**：現物の件数と元記事・版の対応が分かり、原文と生成文を分けて読み出せる。既存通常データを失っていない。
- **サーバだけの探索**：有限の対象で、開発PCのブラウザー・候補生成・常駐同期やCodexの途中指示なしに、候補を見つけて本文を保存する。
- **定期実行の経路**：実際のCron用環境で有限の試験を実行し、MCP・Skill・規約・保存先が使える。試験用予定は終了後に整理し、本運用の予定は未登録または無効にする。
- **初期構築と再開**：有限の試験名簿を進め、区切りで止め、新しいセッションまたはプロセスで保存位置から続ける。全名簿へ自動的に広がらず、毎朝の処理が初期名簿を最初からやり直さない。
- **独立解釈**：指定した少数の保存本文と日時の手掛かりから解釈が進み、結果・失敗・再利用が記録される。原文を上書きせず、試験対象を終えたら停止する。
- **Dashboard**：実画面で検索・一覧・本文・解釈・件数・状態を確認する。未解釈や不明を表示でき、閲覧操作で収集や設定変更が起動しない。
- **運転と保留の維持**：有限の試験は確認用端末やCodexのセッションがなくても進む。通常のサービス再起動後も保存状態と実行経路が使え、本運用の未有効状態が保たれる。OS全体の再起動を必須試験にしない。
- **レビュー資料**：最終Skillの実物・配置版と、対象を先に決めたカバー率調査の量・例・限界が確認できる。

翌朝までの待機は必須にしない。短い単発試験等で実際の定期起動経路を確認し、試験用の予定・子処理を整理する。提案した毎朝の設定と、現時点では有効な本運用の次回予定がないことを分けて報告する。手動スクリプトだけの成功を、Cron経路の確認と読み替えない。

意味の全件検査、全馬の到達証明、カバー率の合格値、速度目標は受入条件にしない。保存・再開・読出し・起動と保留が成立することを確かめ、多発する意味上の偏りが実例で見つかった場合にSkillを小さく改善する。
